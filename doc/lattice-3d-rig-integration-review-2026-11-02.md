# 래티스와 lbsvm-core 3D 리깅 연동 — 검토 (2026-11-02)

래티스 형식 v1(`lattice-editor-ltxm-design-2026-10-29.md`)로 lbsvm-core 의 길이 리그까지 함께 나타낼 수 있는지 검토한다.
목표는 표기 하나로 모든 리깅을 다루는 것이고, 억지로 끼워 맞추는 안이면 받아들이지 않는다. 코드 변경은 없다.
이어받는 문서는 `atlas-rig-unification-design-2026-10-27.md`(이하 통합안)의 §10-3·§16·§17,
`lbsvm-core/doc/Vehicle_Model_Fit_and_Length_Rig_Design.md`(이하 리그 설계)다.

## 1. 결론

**자연스럽게 합쳐진다.** 길이 리그는 래티스 축 하나와 같은 구조이고, 풀이 결과도 실제로 같았다(§3).
새로 만들 개념은 없고, 형식에서 고칠 곳은 셋이다(§4).

- 축을 하나 더 둔다: `Z`. 3D 메시는 축이 셋이다.
- 축 방향에 `z` 를 받는다: `"axis": "+z"`. 이것으로 모델 좌표에서 ISO 8855 로 옮기는 일까지 표기 안에 들어온다.
- 위치 키 `px` 의 이름을 바꾼다. 메시에서는 픽셀이 아니다. 판정 여유 `LAT_EPS` 도 원천 단위에 맞춘다.

반대로 합치면 안 되는 것도 있다. 바퀴는 래티스로 변형하지 않고, 측정 도구의 작업 값은 래티스에 넣지 않는다(§5).

## 2. 대응 관계

### 2-1. 현행 데이터

| 현행(`LB_MODEL_MEASURE`, 사이드카 `measure`) | 래티스 | 비고 |
|---|---|---|
| `clip_volume.y_min`·`y_max` | `X` 축 첫 선·끝 선, 핀 `rear`·`front` | 메시 끝이 뒤범퍼·앞범퍼에 묶인다 |
| `axles_y[i]` | `X` 축 핀 `axle0`, `axle1`, … | 축 번호는 모델 제원 번호 |
| `zone_b[i]`, `zone_f[i]` | 축 둘레의 두 선과 그 사이 고정 구간 | 구간 값 `1` |
| 고정 구간 사이 | 늘림 구간 | 구간 값 `null` |
| `ref.kind` + `ref.mm` | `"ref": {"pins": [a, b], "size": n}` | **10-30 의 기준 치수와 같은 일이다** |
| `unit_mm` | `LAT_Unit()`, 풀이의 k | 쓰지 않고 구한다 |
| `rig.enabled` | 래티스의 유무 | 없으면 끈 것 |
| `slab`, `height_at_y`, `width_at_y`, `length_*_z`, `length_joint_y` | **옮기지 않음** | 측정 도구의 작업 값(§5-2) |

그림에서 겪은 문제와 메시의 문제가 같다는 점이 이 검토의 근거다.

| | 2D 그림 | 3D 메시 |
|---|---|---|
| 배율을 재는 곳 | 그림자를 뺀 차폭의 핀 두 개 | 거울을 뺀 차폭의 핀 두 개(지금은 `clip_volume` 이 거울을 뺀다) |
| 재는 곳 바깥 | 그림자: 핀 바깥이라 실제 크기 유지 | 거울: 핀 바깥이라 실제 크기 유지 |
| 축 둘레 | 바퀴 아치 그림은 고정 | 바퀴 아치 메시는 고정 |
| 나머지 | 적재함 그림은 늘림 | 적재함 메시는 늘림 |

`car_top` 그림과 3D 차체가 같은 핀 이름(`front`, `rear`, `axle0`, `side.l`, `side.r`)을 쓰면 차량 쪽 연결은 하나로 충분하다.
통합안 §16-5 의 "핀은 공유한다"가 여기서 실현된다.

### 2-2. 표기 예: hmc_Xcient2023_12m

리그 설계 부록 A 의 실측값이다. 12 m 모델이므로 길이를 기준 치수로 잡았다. 고정 구간은 축 앞뒤 200 mm 다.

```json5
"lattices": { "body": {
  "version": 1,
  "ref": { "pins": ["rear", "front"], "size": 12000 },      // 1 단위 = 9933.7 mm
  "X": { "axis": "+y",                                      // 결과 X(앞쪽) = 모델 +y
         "at":  [-0.6080, -0.3099, -0.2697, -0.1737, -0.1335, 0.4230, 0.4632, 0.6000],
         "seg": [null,    1,       null,    1,       null,    1,      null],
         "handles": [ { "tag": "rear",  "at": -0.6080 }, { "tag": "axle2", "at": -0.2898 },
                      { "tag": "axle1", "at": -0.1536 }, { "tag": "axle0", "at":  0.4431 },
                      { "tag": "front", "at":  0.6000 } ] },
  "Y": { "axis": "-x",                                      // 결과 Y(왼쪽) = 모델 -x
         "at": [-0.1100, 0.1100], "seg": [null],
         "handles": [ { "tag": "side.l", "at": -0.1100 }, { "tag": "side.r", "at": 0.1100 } ] },
  "Z": { "axis": "+z", "at": [0.0, 0.3], "seg": [null] }    // Z 수치는 자리표시(부록에 실측이 없다)
} }
```

연결은 저장하지 않는다. 핀 `axle0` 의 목표는 거동 제원의 축 위치에서, `front`·`rear` 는 extents 에서 코드가 구한다.
통합안의 세 덩어리(래티스·연결·풀이 결과) 중 연결만 VEH_UNIT 에서 나오는 경우다.

## 3. 실제로 비교한 결과

`LB_LENGTH_RIG_Build` 의 매듭 계산과 ltxm 의 `LAT_SolveAxis` 를 같은 입력으로 돌렸다. 메시 전장을 20,000 등분해 mm 차이의 최댓값을 쟀다.
모델은 Xcient 12 m 실측, 비교 프로그램은 임시로 만들어 저장소에 넣지 않았다.

| 경우 | 최대 차이 | 판단 |
|---|---|---|
| 모델 그대로(12 m) | 0.002 mm | 같다 |
| 14,782 mm 로 늘림 | 0.002 mm | 같다 |
| 9,000 mm 로 줄임 | 0.9 mm | 앞 끝 늘림 구간이 0 인 경우. 옛 코드의 최소 간격 밀기만큼 다르다 |
| 탠덤: 목표에서 고정 구간이 겹침 | 151 mm | **다르다. 래티스가 낫다**(아래) |
| 대응 축이 없는 모델 축, 고정 유지 | 125 mm | **다르다. 정책 결정이 필요하다**(§6-2) |
| 같은 경우, 그 축의 고정을 늘림으로 | 0.002 mm | 같다 |

겹치는 경우 옛 코드는 뒤쪽 선을 밀어 내서 앞뒤로 어긋난다(뒤 축 2,500·앞 축 2,600 목표에 2300·2700·2701·2800).
래티스는 두 축 사이의 고정 구간을 비율대로 줄이고 알린다(2300·2500·2550·2550·2600·2800). 축 위치가 지켜지므로 아치가 바퀴와 어긋나지 않는다.

입력에서 고정 구간이 메시 끝을 넘으면 선이 오름차순이 아니게 되어 래티스 풀이가 틀린 값을 낸다(시험에서 앞 끝이 441 mm 어긋났다).
옛 코드도 이 경우 차가 1 m 길어진다. 옮길 때 끝으로 잘라 내고 `LAT_Validate` 로 알리면 된다.

## 4. 형식에서 고칠 것

아직 래티스를 읽는 코드는 ltxm 뿐이다(lbsvm-core 소스에 없음). 바꾸기에 지금이 가장 싸다.

### 4-1. 세 번째 축 `Z`

X·Y 로 키를 바꾼 것이 여기서 맞아떨어진다. `X`·`Y`·`Z` 는 곧 ISO 8855 의 세 축이다. lon·lat 이었다면 높이 축의 이름이 없었다.
그림은 `Z` 를 쓰지 않는다. `LATTICE.ax[2]` 는 `ax[3]` + 사용하는 축 수가 된다.

### 4-2. `axis` 가 `z` 를 받는다

`"axis"` 는 결과 축이 원천의 어느 방향을 따르는지를 적는다. 메시에 그대로 쓰면 `X = +y`, `Y = -x`, `Z = +z` 가 되어
모델 좌표(+y 앞, +x 오른쪽)에서 ISO 8855 로 옮기는 변환이 된다. 리그 설계 §9-4 의 "ISO 변환을 어디서 끝낼까"에 답이 나온다.
**자산마다 이 세 값으로 적는다.** 다른 좌표계로 만든 모델도 값만 바꾸면 된다.

### 4-3. `px` → `at`

메시에서는 픽셀이 아니므로 이름이 거짓말이 된다. 뜻을 원천 위치로 넓히고 이름을 `at` 으로 바꾸기를 권한다.
옛 키는 X·Y 때처럼 읽어 주고 열 때 고친다. 형식 판은 1 그대로 둔다.
값이 소수가 되므로 ltxm 의 `_put_num`(정수면 정수로) 은 그대로 쓸 수 있다.

### 4-4. `LAT_EPS`

지금 절대값 `1e-4` 다. 픽셀에는 넉넉하지만 Xcient 모델 단위에서는 약 1 mm 에 해당하고, 더 작은 단위의 모델에서는 뜻이 달라진다.
원천 범위에 비례하게 바꾼다(`범위 × 1e-6` 정도). 값은 구현 때 시험으로 정한다.

### 4-5. 고치지 않는 것

- `seg` 의 세 가지 값, `handles`, `ref`, 풀이 규칙. 그대로 맞았다.
- `edge`(soft·hard): 텍셀에만 뜻이 있다. 메시는 읽지 않고 무시한다(통합안 §16-5 3 항). 메시는 늘 이어지는 쪽이다.

## 5. 합치지 않는 것

억지로 합치면 오히려 표기가 망가지는 것들이다.

### 5-1. 바퀴

바퀴는 늘리는 대상이 아니라 축 위치에 찍는 인스턴스다. 차체만 래티스를 타고, 바퀴는 핀과 같은 목표(거동 제원 축 위치)를 받는다.
지금 코드의 "차체 파트만 길이 리그를 탄다"와 같다. 타이어 크기에 따른 바퀴 배율(`wheel_scale_by_tire`)도 그대로 둔다.
차체 띄우기(`body_lift_by_tire`)는 `Z` 축 핀으로 나타낼 수 있어 보이나, 급하지 않아 뒤로 미룬다.

### 5-2. 측정 도구의 작업 값

`slab`, `height_at_y`, `width_at_y`, `length_front_z` 등은 "어디서 재었는가"이지 변형 규칙이 아니다.
래티스의 결과(`at`)만 형식에 넣고, 이 값들은 사이드카의 `measure` 에 도구 전용으로 남긴다. `LB_MODEL_MEASURE` 를 없애지 않고 줄인다.

### 5-3. 모델 축 ↔ 거동 축 대응

`LB_MODEL_FIT_MatchAxles`(그룹별 순서로 짝짓기)는 차량 쪽 연결 규칙이다. 래티스는 핀 이름만 알고 조향 여부를 모른다.
그대로 두고, 그 결과로 핀 목표를 채운다.

### 5-4. 분리형으로 안 되는 변형

캡과 적재함의 폭이 다른 트럭을 폭 방향으로 늘리면, 길이 위치에 따라 폭 배율이 달라야 한다. 축마다 독립인 래티스로는 못 한다.
폭은 모델 값 그대로 두는 것이 기본(리그 설계 §4.3)이라 당장 문제가 되지 않는다. 통합안 §1-2 의 범위 밖 그대로 둔다.

## 7. 단계

단계마다 화면이 바뀌지 않음을 숫자로 확인하고 넘어간다. 앞 단계가 매끄러울 때만 다음으로 간다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **L0 형식 마무리** | §4 를 ltxm 에 반영. 풀이를 lbx-geo 로 옮기고 ltxm 이 그것을 쓴다 | ltxm 자체 시험, 옛 파일 열기 |
| **L1 길이 리그 속 바꾸기** | `LB_LENGTH_RIG_Build` 안을 풀이 호출로. 형식·공개 함수·렌더러는 그대로 | §3 비교를 lbsvm-core 시험에 넣어 통과, svmdemo 화면 동일 |
| **L2 사이드카에 래티스** | `lattices.body` 읽기·쓰기, 옛 `measure` 읽어 변환, 측정 도구가 래티스를 쓴다. `Y`·`Z` 적용(결정 4) | 옛 사이드카 왕복, 다축·굴절 모델 화면 확인 |
| **L3 조인트 하나로** | 차량 조인트 조회를 하나 두고 `TLBBand`·길이 리그가 같이 쓴다 | 축거를 바꾸면 차체·가이드가 함께 움직인다 |
| **L4 DPGL** | 격자를 래티스로(`dpgl_basic`), 옛 격자 어댑터 | 통합안 §17-7 의 승용차 열과 키 값 일치, gl·gfx 화면 동일 |
| **L5 2D 그림** | `TGlyph` → 래티스 메시 + gfx. 차 그림·UI | lbx-gl `TGlyph` 사용처 이관 |
| **L6 S3000ABR** | 앱 `LoadTextureMap` 4 곳, `LoadGlyphFromVariant` 3 곳, 길이 리그 사이드카, 가이드 스프라이트 | 보드 확인, PR |

L1 은 공개 함수와 파일 형식을 건드리지 않으므로 위험이 가장 작고, "자연스럽게 합쳐진다"는 판단을 실제 코드로 검증하는 단계다.
DPGL 마감(11-06)을 생각하면 L4 를 먼저 하고 싶을 수 있으나, 조인트 조회(L3)와 얽혀 있어 L1 부터 차례로 가는 편이 되돌릴 일이 적다.

## 8. 위험

- **매듭과 삼각형.** 매듭에 걸친 긴 삼각형은 꺾이지 않는다. 로우폴리일수록 영향이 크다. 측정 도구가 선을 가까운 에지 루프에 맞춰 준다(통합안 §16-5 5 항, §16-6 4 항). 형식과는 무관하다.
- **노멀 보정.** 지금 코드는 y 만 기울기로 보정한다. `Y`·`Z` 를 늘리면 축마다 같은 계산이 필요하다.
- **검증 범위.** §3 은 X 축 매듭 수치만 비교했다. 실제 화면, `VEH_UNIT_FitAxlesFromModel`(S3000ABR 경로), 다유닛 모델은 아직 보지 않았다. 유닛마다 래티스 하나를 두는 것으로 생각하지만 굴절 모델 자산으로 확인이 필요하다.
- **잔여 사본.** ltxm 의 `ltxm_texmap`·`set_rect_range` 는 옛 격자용 수동 동기화 사본이다. L5 뒤에 어댑터 하나로 줄인다.
