9-slice, DPGL 그리드, 차량 길이 리그처럼 따로 자라 온 "그림이나 메시를 대상에 맞춰 늘이고 붙이는" 기능을

## 1. 목표와 범위

### 1-1. 목표

- **제어점 수에 제한이 없는 하나의 체계.** 9-slice 는 축마다 제어선이 2개뿐이다. 같은 규칙으로 축마다 몇 개든
  둘 수 있어야 한다(N-slice). 버튼 그림에도 중간 제어선을 둘 수 있어야 한다.
- **대상을 가리지 않는다.** 같은 데이터 형식, 같은 풀이 함수로 다음을 모두 다룬다.
  - 화면 사각형에 붙는 UI 그림(버튼, 패널, 그림자·글로우가 바깥으로 나가는 그림)
  - 차량 크기에 붙는 2D 그림: 탑뷰 차 그림, 측면도. 축거가 바뀌면 바퀴와 그 주변 픽셀이 축을 따라 움직인다.
  - 차량 운동을 따라 쓸리는 띠: 동적 가이드, 고정 가이드, 바퀴 궤적, 차가 쓸고 가는 영역
  - 3D 메시: 지금의 길이 리그(축 주변 고정, 나머지 늘림). 나중에는 폭·높이 방향도 같은 방식으로.
- **디자인과 배치를 나눈다.** 그림을 그리는 쪽이 정하는 것(어느 선이 제어선이고 어디가 모양을 유지하는가)과
  차종·용도마다 정하는 것(그 제어선이 차량의 어디에 붙는가)을 다른 데이터에 둔다.
- **단순한 경우는 지금처럼 단순하게.** 경계만 그으면 전부 늘어나고, 슬라이스선만 그으면 9-slice 가 되는 지금의
  사용감을 유지한다. 지정할 것이 늘어나는 것은 차량 조인트에 붙일 때뿐이다.

### 1-2. 범위 밖

- 제어점 여러 개의 가중치를 섞는 일반 스키닝. 분리형으로 안 되는 변형은 §6-5 의 래티스 노드로 먼저 해결해 보고,
  그래도 부족할 때 따로 검토한다.
- 시간 축 애니메이션. 이 체계는 "지금 이 상태에서 어디에 놓이는가"만 다룬다. 애니메이션은 컨스트레인트에 들어가는
  값(관절각, 조향)을 바꾸는 쪽이다.
- 가이드 맵을 어떻게 굽고 나누는가(맵 그룹·메모리 예산)는 §12 결정 사항으로만 적는다.

## 2. 현재 상태

### 2-1. 데이터: PNG 안의 "mesh" 청크

아틀라스 PNG 에 JSON 청크를 넣어 둔다. 코어 `lbsvm_model_2d.cpp` 의 `LoadTextureMap`/`SaveTextureMap` 이 읽고
쓰며, ltxm 은 이 함수들을 `ltxm_texmap.cpp` 로 옮겨 와 손으로 맞추고 있다.

```json5
{ "grids": {
    "Car":  { "x": [45, 66, 85, 275, 488, 511], "y": [0, 30, 50, 199, 219, 256],
              "x_tag": [...], "y_tag": [...], "axis": 0 },
    "DPGL": { "x": [...], "y": [...], "x_tag": ["0", "axle", "1500", ...], "y_tag": [...] } } }
```

축마다 픽셀 위치 배열과 태그 배열을 나란히 둔다. 태그 하나로 그리드 하나를 여러 용도(9-slice, DPGL)에 쓰려는
설계였다.

### 2-2. 9-slice 태그의 원래 뜻

| 지정 | 동작 | 목적 |
|---|---|---|
| 외곽만 | 전부 늘림 | 단순한 그림 |
| `b` | 테두리 바깥은 모양 유지, 안쪽은 늘림. `f` 는 암묵적으로 외곽 | 늘어나도 바깥 모양 유지 |
| `b` + `f` | `f` 가 대상 사각형에 붙고, `f` 바깥은 대상 밖으로 나가며 모양 유지 | 그림자·글로우 |
| `x` | `b` 와 같고 가운데를 그리지 않음 | 액자 모양 |

코드(`lbx_gl_class.cpp` `TGlyph::FillVertexList`, `lbsvm_model_2d.cpp` `set_rect_range`) 확인 결과:

- `f` 는 대상 끝에 맞춰지고, 외곽은 `f` 에서 원천 길이 × 배율만큼 바깥으로 밀려난다. `b` 는 외곽에서부터 잰다.
  그래서 외곽 ≤ `f` ≤ `b` 순서일 때만 맞게 동작한다.
- 축마다 `b` 2개, `f` 2개까지만 받는다.
- `x` 는 어느 축에 붙든 글리프 전체 플래그 하나(`SetBorder(..., perforated)`)가 된다. 태그 자리에 있지만 실제로는
  2D 속성이다.

### 2-3. 해석기 네 가지

| 해석기 | 위치 | 읽는 것 | 규칙 |
|---|---|---|---|
| `LoadGlyphFromVariant` → `TGlyph` | lbsvm-core / lbx-gl(폐기 예정) | `grids[0]` | §2-2 |
| `LoadBandFromVariant` → `TLBBand` | lbsvm-core | `grids.DPGL` | 길이 방향 `"0"` = 뒤범퍼, 숫자 = 범퍼에서 mm, `"axle"` = 축. 폭 방향 숫자 = 옆면에서 안쪽 mm, `"center"` 를 지나면 좌우 반사 |
| `LB_LENGTH_RIG` | lbsvm-core | 사이드카 `measure` 블록 | 모델 메시의 축 위치와 축마다 고정 구간(`zone_f`/`zone_b`). 고정 구간은 모양을 유지한 채 축과 함께 이동하고 사이는 늘어난다. 결과는 `y_in`→`y_out` 매듭 열 |
| S3000ABR `GuidelineRenderSystem` | s3000abr 앱 | 코드 상수 | guide-s3000.png 의 스프라이트 사각형과 9-slice 머리 48 px 고정을 상수로 지정. 거리 구간 경계는 전장에 비례(전장 6 m 이면 빨강 경계가 1.8 m) |

### 2-4. 문제

1. **태그 한 칸이 성격이 다른 것을 함께 맡는다.** 모양 유지 영역의 끝(`b`), 대상에 붙는 위치(`f`, DPGL 의 mm),
   차량 위의 이름(`"axle"`), 축 전체 속성(`"center"` 반사), 2D 속성(`x`). 그래서 해석기마다 규칙이 따로 생겼고,
   9-slice 와 그리드 사이에 공통 규칙이 거의 없다.
2. **디자인과 물리 좌표가 한 청크에 있다.** 거리 표시를 바꾸려면 그림의 격자를 고쳐야 하고, 차 크기가 다르면
   그림도 따로 있어야 한다. 원래 의도는 ltxm 하나로 가이드 위치까지 고치는 것이었다(§11-3 에서 살린다).
3. **제어선 수가 해석기마다 고정이다.** 9-slice 는 축마다 2개다. DPGL 그리드는 수가 자유롭지만 모양 유지 규칙이 없다.
4. **같은 일을 하는 자료형이 따로 있다.** 길이 리그는 매듭 열인데 그리드와 다른 형식·다른 코드다.
5. **청크 입출력이 두 벌이고 텍스처 생성과 묶여 있다.** 코어와 ltxm 에 사본이 있고, 청크 읽기가 lbx-gl
   텍스처 생성(`TGLTexture2D`)과 한 함수다. S3000ABR 은 `LoadTextureMap` 이 파일을 열지 못했을 때 그대로 진행해
   죽는 문제를 호출부 네 곳에서 따로 막고 있다(lbsvm-app `SVMRenderSystem.cpp`).
6. **그리는 코드가 폐기 예정인 lbx-gl 에 있다.** `TGlyph`, `TLBBandRenderer`.

## 3. 핵심 개념

### 3-1. 리그·래티스·컨스트레인트·공간

| 용어 | 이 체계에서의 뜻 | 쓰이는 곳 |
|---|---|---|
| **리그(rig)** | 뼈대. 차량 스펙(유닛·축·바퀴·히치·차체 외곽)이 리그다. 굴절각은 관절 각도다 | 3D 리깅 |
| **조인트(joint)** | 리그 위의 이름 붙은 점·선. `front_bumper`, `axle[1]`, `side.left` … | 3D 리깅 |
| **래티스(lattice)** | 그림·메시 쪽 데이터. 축마다 제어선 열이 있고, 그 곱이 칸을 만든다 | 래티스 디포머(FFD) |
| **컨스트레인트(constraint)** | 래티스의 핀 이름 → 공간 안의 위치 식(조인트 ± 거리) | 3D 리깅(point constraint) |
| **공간(space)** | 조인트를 실제 값으로 풀고 결과를 놓는 문맥. RECT·BODY·SWEEP | 3D 리깅(world/local space) |

메시, 2D 차 그림, 가이드, 그림자, 투영면은 모두 조인트 이름으로 리그에 붙는 껍데기다. 조인트 이름은 하나만
둔다. 앵커로 정하는 광선 뷰 설계(`lbsvm-core/doc/Anchored_Ray_View_Design.md`)의 앵커 어휘, 차량 영역이 바뀌면
투영면·그림자·TP 가 따라가야 한다는 과제도 같은 이름을 쓴다.

### 3-2. 세 층

| 층 | 무엇을 정하나 | 누가·어디서 | 단위 |
|---|---|---|---|
| **래티스(디자인)** | 원천 영역, 축마다 제어선(외곽·핀·슬라이스선)과 핀 이름, 반복 구간, 칸 표시(자동) | 그림을 그리는 쪽. ltxm | 원천 단위(px, 모델 mm) |
| **컨스트레인트(배치)** | 핀 이름 → 공간 안의 식, 고정 영역 배율 | 쓰는 쪽. 차종 파일, 가이드 정의, UI 배치 | 목표 단위(mm, 화면 px) |
| **공간(문맥)** | 조인트 풀이, 결과를 최종 좌표로 옮기는 방법 | 코드 | — |

래티스와 컨스트레인트는 **핀 이름**으로만 만난다. 같은 래티스를 여러 차종·여러 크기에 다시 쓰고, PC 툴의
튜닝(폭·길이·오프셋)은 컨스트레인트만 바꾼다. 슬라이스선은 디자인에만 속하고 컨스트레인트를 갖지 않는다.

### 3-3. ECS 로 본 구조

| 엔티티 | 컴포넌트 | 읽는 쪽 |
|---|---|---|
| 스프라이트(원천 영역) | 이름, 사각형 또는 메시 범위, 원천 단위 | 모두 |
| 축 | 방향(뒤집기·가로세로 교환), 반사 | 모두 |
| 제어선 | 원천 위치, 종류(외곽·핀·슬라이스선), 이름(핀만) | 풀이 |
| 구간(이웃 제어선 사이) | 반복 여부(선택) | 메시 생성 |
| 칸(두 축 구간의 곱) | 빈 칸·불투명 칸(자동), 수동 지정(선택) | 메시 생성 |
| 컨스트레인트 | 핀 이름 → 식, 배율 규칙 | 풀이 |
| 래티스 노드(선택) | 2D 오프셋 식 | 레벨 2 풀이 |

모르는 컴포넌트는 지나친다. 처음 태그 체계가 노린 "같은 데이터를 여러 용도로"를 규칙을 깨지 않고 이룰 수 있다.
ECS 와 다른 점은 제어선이 축 안에서 순서를 갖고 원천 위치가 단조 증가해야 한다는 것뿐이다.

## 4. 제어선 규칙

> 검토 중: 이 절은 고정·늘림을 핀과 슬라이스선의 관계에서 추론한다. 저장 데이터에 구간 성질을 직접 적고 추론은
> 편집기와 옛 데이터 변환기에만 두자는 의견이 있다(§15-1, §15-2). 결론은 아직 내리지 않았다.

### 4-1. 제어선 세 종류

| 종류 | 표기 | 뜻 | 옛 태그 |
|---|---|---|---|
| 외곽 | 없음 | 원천 영역의 두 끝. 축마다 항상 2개 | 없음 |
| 핀 | `p` | 공간 안의 위치에 붙는 선. 이름을 가질 수 있다 | `f` |
| 슬라이스선 | `s` | 모양을 유지하는 고정 영역이 끝나는 곳 | `b` |

외곽에도 `p` 를 붙일 수 있다(길이 리그의 앞·뒤 범퍼처럼 끝이 목표에 붙는 경우).

### 4-2. 규칙 하나

> **가장 바깥 핀의 바깥(아웃셋)과, 각 핀에서 그 핀에 속한 슬라이스선까지는 모양 유지(고정). 나머지는 늘림.**

- **아웃셋**은 늘어날 기준이 없으므로 항상 고정이다. 그림자·글로우가 이 영역이다. 아웃셋 쪽에 있는 슬라이스선은
  뜻이 없으므로 무시하고 경고한다.
- **암묵 핀**: 컨스트레인트를 가진 핀이 축에 하나도 없으면 두 외곽이 핀이 된다(이름 `start`/`end`). 슬라이스선만
  그은 9-slice 가 이 경우다.
- **컨스트레인트 없는 핀**은 떠 있는 고정 영역이 된다. 양옆 늘림 구간이 남는 길이를 원천 길이 비율로 나눠
  가지므로 그 사이에 놓인다(버튼 가운데 아이콘).

### 4-3. 슬라이스선의 소속

이웃한 두 핀 A < B 사이의 슬라이스선 개수로 정한다.

| 개수 | 소속 | 결과 |
|---|---|---|
| 0 | 없음 | A~B 전부 늘림 |
| 1 | 원천 거리가 더 가까운 핀 | 그 핀 쪽만 고정, 나머지 늘림 |
| 2 | 앞의 것은 A, 뒤의 것은 B | 고정 · 늘림 · 고정 |
| 3 이상 | — | 오류. 가운데 고정 영역은 컨스트레인트 없는 핀으로 나타낸다 |

- 두 고정 영역이 맞닿는 경우(탠덤 축)는 슬라이스선 두 개를 같은 자리에 둔다. 늘림 구간 길이가 0 이 된다.
  편집기는 두 선을 하나로 그리되 데이터에는 둘로 저장한다.
- 1개일 때 거리가 같으면 오류로 알린다.
- 1개일 때 "가까운 핀" 규칙은 고정 영역이 두 핀 거리의 절반보다 길면 엉뚱한 핀에 붙는다(예: 앞 오버행이 짧은데 앞축
  고정 구간이 긴 차). 편집기는 슬라이스선마다 소속 핀을 표시하고, 이런 경우 반대쪽 핀 자리에 슬라이스선을 하나 더
  두어(그쪽 고정 폭 0) 개수 2 로 만들게 한다.
- 목표가 짧아 고정 영역이 실제로 겹치면 §7-3 의 줄어들 때 규칙으로 처리한다.

### 4-4. 옛 세 단계와 축 리그가 이 규칙에서 나온다

| 경우 | 제어선 | 규칙 적용 결과 |
|---|---|---|
| 외곽만 | 외곽 2 | 컨스트레인트 있는 핀 없음 → 외곽이 암묵 핀, 사이 슬라이스선 0 → 전부 늘림 |
| `b` 만 | 외곽 2 + `s` 2 | 외곽이 암묵 핀, 사이 슬라이스선 2 → 고정·늘림·고정(9-slice) |
| `b` + `f` | 외곽 2 + `p` 2 + `s` 2 | 핀 사이 슬라이스선 2 → 고정·늘림·고정, 핀 바깥은 아웃셋(고정, 대상 밖으로 나감) |
| `f` 만 | 외곽 2 + `p` 2 | 핀 사이 전부 늘림, 아웃셋만 모양 유지 |
| 3D 길이 리그 | 외곽(범퍼 핀) 2 + 축마다 `p` 1 + `s` 2 | 축마다 고정 영역, 축 사이와 범퍼~축 사이 늘림 |
| N-slice | 핀·슬라이스선 아무 개수 | 같은 규칙 |

## 5. 칸 층: 빈 칸과 불투명 칸

### 5-1. 비움은 칸의 성질이다

9-slice 의 구멍은 가운데 한 칸만 비운다. 축 하나의 성질로는 나타낼 수 없다(x 축 가운데 구간을 비우면 그 열
전체가 사라진다). 그래서 비움은 칸(두 축 구간의 곱)에 둔다.

### 5-2. 편집기가 저장할 때 자동으로 판정한다

- 칸마다 텍셀을 검사한다.
  - 알파가 전부 0 이면 **빈 칸**: 메시를 만들지 않는다.
  - 알파가 전부 255 이면 **불투명 칸**: 블렌딩 없이 그릴 수 있다(보드의 채우기 부담을 줄인다).
- **판단 범위는 텍셀 중심이 칸 안에 있는 것만**으로 한다. 이웃 1 텍셀까지 넣으면, 불투명한 테두리와 맞닿는 액자
  가운데 칸이 빈 칸으로 판정되지 않는다. 또 가운데를 그리면 경계의 반 텍셀 번짐이 늘림 배율만큼 넓어져, 테두리가
  안쪽으로 흐릿하게 번진 띠로 보인다. 자기 텍셀만 보는 규칙이 옛 `x` 와 같은 결과를 낸다.
- 판정 결과와 함께 픽셀 데이터의 해시를 저장한다. 읽을 때 해시가 다르거나(다른 툴에서 PNG 를 고친 경우) 판정이
  없으면 다시 계산하고 경고를 한 번 남긴다. 아틀라스 하나에 로드 시점 몇 ms 이고, 매 프레임 하는 일은 없다.
- 손실 압축(ASTC 등)을 쓰게 되면 압축 전 원본에서 판정한다.

### 5-3. 수동 지정은 예외로

내용이 있어도 숨기고 싶은 칸은 핀 이름 범위로 지정한다. 수동 지정이 자동 판정보다 우선한다.

```json5
"cells": [ { "x": ["icon", "r"], "y": ["start", "end"], "fill": false } ]   // §6-1 btn_wide 의 오른쪽 절반
```

## 6. 데이터 형식

### 6-1. 래티스(디자인)

축마다 나란한 배열로 쓴다. 제어선 열은 길이 n, 구간 열은 길이 n−1 이다.

```json5
{ "lattices": {
  // 버튼: 양끝 핀, 가운데 아이콘 핀(컨스트레인트가 없으면 가운데에 뜬다), 각 핀 둘레 고정
  "btn_wide": { "rect": [0, 0, 120, 48], "unit": "px",
    "x": { "px":   [0,   12,  40,  60,     80,  108, 120],
           "kind": ["p", "s", "s", "p",    "s", "s", "p"],
           "name": ["l", null, null, "icon", null, null, "r"] },
    "y": { "px":   [0, 12, 36, 48],
           "kind": ["", "s", "s", ""] } },            // 핀 없음 → 외곽이 암묵 핀(9-slice)

  // 가이드 스프라이트: 폭 방향 선·발, 길이 방향 먼 끝 머리 48 px 고정
  "pgl_rgy": { "rect": [392, 0, 96, 576], "unit": "px",
    "u": { "px": [0, 96], "kind": ["p", "p"], "name": ["line", "foot"] },
    "v": { "px":   [0,     48,  384,   576],
           "kind": ["p",   "s", "p",   "p"],
           "name": ["far", null, "mid", "near"],
           "span": [null, null, "repeat"] } },        // mid~near 는 반복(예시)

  // 탑뷰 차 그림: 범퍼·축이 핀, 축 둘레 고정, 좌우 바깥 20 px 는 그림자(아웃셋)
  "car_top": { "rect": [0, 0, 512, 256], "unit": "px",     // 차를 가로로 눕힌 그림: x = 길이, y = 폭
    "x": { "px":   [10,      60,  85,      110, 400, 425,     450, 500],
           "kind": ["p",     "s", "p",     "s", "s", "p",     "s", "p"],
           "name": ["front", null, "axle0", null, null, "axle1", null, "rear"] },
    "y": { "px":   [0, 20, 236, 256],
           "kind": ["", "p", "p", ""],
           "name": [null, "side.l", "side.r", null] } } } }
```

`car_top` 의 x 축에 규칙을 적용하면 이렇게 된다.
- front(10)~axle0(85) 사이 슬라이스선 60 은 axle0 쪽이 가깝다(25 대 50). 그래서 front~60 늘림, 60~85 고정.
- axle0~axle1 사이 110·400 은 하나씩 나뉘어 85~110 고정, 110~400 늘림, 400~425 고정.
- axle1~rear 사이 450 은 axle1 쪽이 가깝다. 그래서 425~450 고정, 450~500 늘림.
- y 축은 핀 side.l·side.r 바깥 20 px 가 아웃셋이 되어 그림자가 차폭 밖으로 같은 모양 그대로 나간다.

축 속성은 `"flip": true`(원천 축 뒤집기), `"swap": true`(가로세로 교환, 옛 `"axis": 1`),
`"mirror": "<핀 이름>"`(그 핀을 지나면 반대쪽으로 반사, 옛 `"center"`)로 쓴다.
원천이 3D 메시이면 `"unit": "model"` 이고 `rect` 대신 범위를 쓴다.

### 6-2. 컨스트레인트(배치)

```json5
// 차종 파일 안: BODY 공간, 래티스 car_top
"constraints": { "space": "body", "unit": 0, "lattice": "car_top",
  "x": { "front": "front_bumper", "axle0": "axle[0]", "axle1": "axle[1]", "rear": "rear_bumper" },
  "y": { "side.l": "side.left", "side.r": "side.right" } }

// 가이드 정의 안: SWEEP 공간, 래티스 pgl_rgy
"constraints": { "space": "sweep", "lattice": "pgl_rgy",
  "u": { "line": "side.left + 500", "foot": "side.left + 250" },   // 선은 미러 여유 바깥, 발은 차 안쪽으로 250 mm
  "v": { "near": "u = 0", "mid": "u = 2000", "far": "u = 5000" },
  "scale": { "v": "cross" } }

// UI 배치: RECT 공간, 래티스 btn_wide (icon 은 컨스트레인트 없이 가운데에 뜬다)
"constraints": { "space": "rect", "lattice": "btn_wide",
  "x": { "l": "left", "r": "right" } }                 // y 는 암묵 핀 start/end → top/bottom
```

RECT 공간에서 암묵 핀 `start`/`end` 는 컨스트레인트를 쓰지 않아도 사각형 두 끝에 붙는다.

### 6-3. 식 문법(최소)

```
식    := 항 ( ('+' | '-') 수치 단위? )*
항    := 조인트 | 'u' '=' 수치 | 'mix(' 조인트 ',' 조인트 ',' 비율 ')'
단위  := 'mm' | 'px' | '%'      (생략하면 공간의 기본 단위)
```

- 조인트 이름은 공간이 푼다(§8). 모르는 이름은 오류로 알리고 그 핀을 컨스트레인트 없는 핀으로 다룬다.
- `%` 는 같은 축 두 끝 조인트 사이 길이의 비율이다(예: 차폭의 10 %).
- 처음에는 이 정도만 둔다.

### 6-4. 저장 위치

- **래티스**: 아틀라스 PNG 청크를 그대로 쓰되 키를 `lattices` 로 둔다. 옛 `grids` 는 읽기만 하고 변환한다(§10).
  사이드카 JSON 으로 뺄지는 §12 에서 정한다.
- **컨스트레인트**: 쓰는 쪽 파일. 차량 그림·메시는 차종 파일(저장 체계 통일 스키마의 차량 문서), 가이드는 가이드
  정의 파일, UI 는 UI 배치 파일.

### 6-5. 레벨 2: 래티스 노드(선택)

분리형으로 안 되는 변형(바퀴 하나만 들리는 표현 등)은 래티스 노드(두 축 제어선의 교차점)에 2D 오프셋 식을
붙인다. 분리형으로 먼저 풀고 노드 오프셋을 칸 안에서 쌍선형으로 섞는다(FFD 와 같은 방식). 필요해질 때 넣는다.

```json5
"nodes": [ { "at": ["axle1", "side.r"], "offset": ["0", "lift[1] * 0.5"] } ]
```

## 7. 풀이: 축 하나

축마다 따로 푼다. 입력은 제어선(원천 위치·종류), 핀 컨스트레인트의 목표 값, 고정 영역 배율 k 다.

### 7-1. 순서

1. 핀을 정한다. 컨스트레인트를 가진 핀이 없으면 외곽을 암묵 핀으로 둔다. 컨스트레인트 목표 값은 원천 순서를 따라
   모두 증가하거나 모두 감소해야 한다. 모두 감소하면 축이 뒤집혀 놓인 것으로 본다(가이드 스프라이트의 먼 끝이
   원천 위쪽에 있는 경우). 섞여 있으면 오류로 알리고 어긋난 핀의 컨스트레인트를 버린다.
2. 슬라이스선을 핀에 나눠 준다(§4-3). 고정 영역 = 아웃셋 + 각 핀과 그 슬라이스선 사이.
3. 컨스트레인트를 가진 이웃한 두 핀 사이마다:
   - 목표 길이 L, 고정 길이 합 F = k × (고정 영역 원천 길이 합. 사이에 뜬 핀의 고정 영역 포함), 반복 구간 합 R
     (반복 단위의 정수배)
   - 남는 길이 L − F − R 을 늘림 구간이 원천 길이 비율로 나눠 갖는다.
4. 가장 바깥 핀의 바깥은 모든 구간을 k 로 이어 붙인다(아웃셋).

### 7-2. 고정 영역 배율 k

컨스트레인트의 `scale` 로 정한다.
- 수치: 원천 단위당 목표 단위(화면 DPI 배율, mm/px, 모델 mm → 실제 mm)
- `"cross"`: 다른 축에서 실제로 나온 배율. 가이드 스프라이트 머리 길이가 띠 폭을 따라가게 하는 방법이다.
  S3000ABR 이 띠 폭 96 px = 250 mm 로 머리 48 px 를 125 mm 로 바꾸는 것과 같다.
- `"pins"`(기본): 이 축에서 컨스트레인트를 가진 첫 핀과 마지막 핀 사이 배율

### 7-3. 줄어들 때

목표 길이가 고정·반복 합보다 짧으면(작은 차, 짧은 버튼):
- 기본: 고정 영역도 같은 비율로 줄이고, 처음 한 번만 경고를 남긴다.
- 반복 구간은 0회까지 줄인다.

### 7-4. 출력

축마다 제어선의 목표 위치 배열. 메시 생성(§9)과 정점을 직접 옮기는 쪽(길이 리그)이 이 배열을 쓴다.

## 8. 공간

### 8-1. RECT — 화면 사각형

- 조인트: `left`, `right`, `top`, `bottom`, `center`(축별). 기본 단위 px. 출력은 화면 2D.
- 쓰는 곳: 9-slice·N-slice UI, 지금의 `TGlyph`.

### 8-2. BODY — 유닛 차체

- 조인트(유닛 k 의 VEH_SPEC 에서): `front_bumper`, `rear_bumper`, `axle[i]`, `axle[i].wheel[j]`,
  `side.left`/`side.right`, `center`, `ground`, `roof`, `hitch.front`/`hitch.rear`
- 축: x(길이), y(폭), z(높이). 기본 단위 mm. 출력은 유닛 좌표이고 유닛 자세(관절각 반영)로 월드에 놓인다.
- 쓰는 곳: 탑뷰 차 그림(x·y), 측면도(x·z), 3D 메시 길이 리그(x). 앞으로 폭·높이 리그와 그림자·투영면의 영역
  추종.

### 8-3. SWEEP — 운동을 따라 쓸리는 띠

모델링의 sweep(프로파일을 경로를 따라 쓴다)과 같은 구성이다.

- **경로 매개변수 u**: 기준점이 운동을 따라 이동한 거리(mm). u = 0 이 지금 자세다.
- **프로파일**: 차체에 붙은 선분. BODY 조인트 식 두 개로 정한다(예: 뒤범퍼 위의 `side.left + 500` ~
  `side.right - 500`). 래티스의 폭 방향 축이 이 선분 위에 놓인다.
- 정점 = 자세(u) · 프로파일 점. 자세(u)는 유닛의 운동 경로(`LBSVM_BAND_PATH`, 위치·방향 표본)에서 읽는다.
- 기준점은 회전 중심에서 차축선에 내린 수선의 발로 둔다. 그러면 4WS 에서도 경로 접선과 차 방향이 같고, 굴절차
  트레일러는 축 중심이 차 방향으로만 움직이므로 같은 데이터로 된다.
- 프로파일을 무엇으로 고르느냐에 따라 다음이 모두 같은 코드로 된다.

  | 프로파일 | 결과 |
  |---|---|
  | 뒤범퍼 선분 | S3000ABR 의 동적 가이드와 같은 의미. u = 0 은 지금 범퍼 자리이고 거리 표시가 회전 중심 쪽 반경선 위에 놓인다 |
  | 뒤 축 선분 | 지금의 TLBBand 결과(축 원호의 평행선). 비교용 |
  | 바퀴마다 타이어 폭 | 바퀴 궤적 |
  | 차체 외곽 선분 여러 개 | 차가 쓸고 가는 영역. 맵에 겹쳐 그리면 합집합이 된다 |
  | 경로가 직선(곡률 0) | 고정 가이드 |

- u 의 조인트: `u = 수치` 외에 BODY x 조인트를 쓰면 "그 차체 선이 지금 있는 자리"(u < 0, 차 밑 구간)를 뜻한다.
  지금 DPGL 그리드의 `"axle"` 태그가 이것이다.
- 테셀레이션: 늘림 구간을 최대 변 길이로 다시 나눈다(지금 `TLBBand::SetMaxEdge` 와 같은 일).

## 9. 메시 출력

- 정점: 축마다 (제어선 + 테셀레이션 점) 위치의 곱. UV = 원천 위치 / 아틀라스 크기.
- 빈 칸은 건너뛴다. 불투명 칸은 따로 모아 블렌딩 없이 그릴 수 있게 표시해 둔다.
- 반복 구간은 반복 경계에서 정점을 나눠 UV 를 다시 시작한다.
- 출력은 평범한 배열(위치, UV, u16 인덱스)이다. 래티스는 그리지 않는다. 그리기는 lbx-gfx(BLIT 메시, 가이드 맵
  굽기)가 맡는다. lbx-gl 은 폐기 예정이므로 새 그리기 경로를 lbx-gl 에 만들지 않는다.
- 레벨 2 노드가 있으면 정점마다 오프셋을 쌍선형으로 더한다.

## 10. 현행 기능 옮기기

### 10-1. 9-slice (`TGlyph`)

| 옛 태그 | 새 표현 |
|---|---|
| 없음(외곽) | 외곽 |
| `b` | `s` |
| `f` | `p`, 이름 `fit.l`/`fit.r`(축별). RECT 컨스트레인트 `left`/`right` |
| `x` | `s` + 가운데 칸 수동 지정 `fill: false`. 옛 동작을 그대로 지키려고 자동 판정에 맡기지 않는다 |
| `axis` | 축 `swap` |

옛 `grids` 를 읽으면 이 표대로 래티스와 기본 컨스트레인트를 만든다. 같은 화면이 나오는지 먼저 확인한다.

### 10-2. DPGL 그리드 (`TLBBand`)

| 옛 태그 | 새 표현 |
|---|---|
| 길이 `"0"`, 숫자 | 핀 `d0`, `d1500` … SWEEP 컨스트레인트 `u = 수치` |
| 길이 `"axle"` | 핀 `axle`, 컨스트레인트 `u = 축 x 조인트`(차 밑 구간) |
| 폭 숫자 | 핀, 컨스트레인트 `side.left + 수치` / `side.right - 수치` |
| 폭 `"center"` | 축 `mirror` |

슬라이스선이 없으므로 핀 사이는 전부 늘어난다(지금 동작과 같다). 옛 그리드는 프로파일을 "뒤 축 선분"으로 읽는다.

> 정정(2026-10-28, §17-8): 숫자 태그를 전부 핀으로 두면 경계 핀 일부만 옮겼을 때 발·틈 키가 명목 위치에 남아
> 순서가 뒤집힌다(초록 먼 끝은 -10000 으로 갔는데 발 안쪽 끝은 -2900 에 남는다). 옛 그리드는 §17-8 의 어댑터
> 규칙으로 읽는다.
지금 화면과 같게 나오므로 비교 기준으로 쓴다.

### 10-3. 길이 리그 (`LB_LENGTH_RIG`)

- 원천 = 모델 메시 mm, x 축 하나. 제어선 = 메시 앞뒤 외곽(핀 `front`/`rear`), 축 중심(핀 `axle[i]`), 축마다
  고정 구간 두 끝(`s`).
- 컨스트레인트: BODY `front_bumper`, `axle[k]`, `rear_bumper`. 배율 k = `unit_mm`(수치).
- `LB_MODEL_MEASURE` 는 메시의 래티스가 되고 `LB_LENGTH_RIG_Build` 는 래티스 + 컨스트레인트 풀이로 바뀐다.
  공개 함수는 한동안 그대로 두고 안쪽만 바꾼다. 축 구간이 맞닿는 탠덤 축은 같은 자리 슬라이스선 둘로 나타낸다.

### 10-4. S3000ABR 가이드 스프라이트

- guide-s3000.png 의 사각형과 머리 48 px 고정을 래티스로 옮긴다(머리 = 먼 끝 핀 + 슬라이스선 하나).
- 거리 경계는 컨스트레인트 `u = 1500` 처럼 절대값이 되어, 전장을 바꿔도 빨강 경계가 1.5 m 에 남는다.
- 띠 폭은 폭 방향 핀 컨스트레인트, 머리 길이는 `scale: cross` 로 지금 동작과 같게 둔다.

### 10-5. 탑뷰·측면 차 그림

- 지금은 `grids[0]` 9-slice 를 `FitTo` 로 차량 영역에 맞춘다.
- 새 체계에서는 BODY 컨스트레인트로 범퍼·옆면에 맞추고, 축 핀을 `axle[i]` 에 붙인다. 축거가 다른 차종에서 바퀴
  그림이 축을 따라간다(§6-1 `car_top`).

## 11. 코드 배치

경계 원칙: 차량과 무관한 범용 기하는 lbx, 차량 의미는 lbsvm-core, 덩치 큰 편집 기능은 툴.

### 11-1. lbx

- `lbx-geo` `lbx_lattice.h/.c`(가칭): 제어선·구간·칸 자료형, 슬라이스선 소속 규칙, 축 풀이, 식 파서(조인트
  조회는 콜백), 칸 자동 판정(알파 버퍼를 받아 빈 칸·불투명 칸), 래티스 메시 생성(공간은 콜백), RECT 공간.
  GL 없는 C.
- 래티스 청크 입출력(PNG 청크 ↔ var): 지금 `lbsvm_model_2d.cpp` 와 ltxm 사본으로 나뉜 것을 lbx 로 옮겨 한 벌로
  만든다. lbx-core 이미지 입출력(`LBX_IMAGE` 청크 콜백) 위에 두고 텍스처 생성과 떼어 둔다. 텍스처는 쓰는 쪽이
  gfx 로 만든다. 파일을 열지 못하면 오류를 돌려준다(S3000ABR 호출부의 방어 코드가 필요 없어진다).

### 11-2. lbsvm-core

- `lbsvm_rig.h/.cpp`(가칭): VEH_SPEC 조인트 풀이, BODY·SWEEP 공간, 프로파일 선분, 운동 경로(`LBSVM_BAND_PATH`).
- `TLBBand` 는 SWEEP 공간 래티스로 다시 구현하거나 옛 그리드 읽기 경로로만 남긴다(P2 에서 정한다).
  `TLBBandRenderer`(lbx-gl 버퍼)는 gfx 가이드 맵 경로로 대체하고 lbx-gl 과 함께 정리한다.
- 가이드 정의(래티스 이름 + 컨스트레인트 + 맵 그룹)와 `LBSVM_GUIDE_MAP` 의 띠 여러 개 굽기.
- 길이 리그(`lbsvm_model_fit`)를 BODY 래티스 위로.

### 11-3. 툴

- **ltxm**: 래티스 편집(축마다 제어선 추가·삭제·종류·핀 이름·반복 구간), 저장할 때 칸 자동 판정. 차종
  컨스트레인트 파일 하나를 미리보기 대상으로 열어 두고 디자인과 배치를 한 화면에서 고친다. 저장할 때 디자인은
  PNG 청크로, 배치는 컨스트레인트 파일로 나눠 쓴다. ltxm 만으로 가이드 위치를 고친다는 처음 의도는 이렇게 살린다.
- **차량 툴**(Model Spec 창 계열): 메시 래티스(측정)와 BODY 컨스트레인트.
- svmdemo 안의 옛 그리드 편집기(`svmdemo_grid`·`svmdemo_uvmap`, `USE_UVMAP_EDITOR 0`)는 수정하지 않는다.

### 11-4. lbx-gl 폐기에 따른 이관

| 사용처 | 쓰는 것 | 옮기는 시점 |
|---|---|---|
| svmdemo `car_glyph` | 탑뷰 차 그림을 `dl_scene->AddGlyph` 로 차량 영역에 | P1. 래티스 경로의 첫 사용처 |
| S3000ABR lbsvm-app `SVMRenderSystem` | `car_glyph`·`custom_glyph`·`assist_glyph` 세 개, `LoadTextureMap` 호출 네 곳 | lbsvm-core 가 gfx 로 전환을 마친 뒤 S3000ABR 에 한꺼번에 적용한다는 기존 방침(2026-07-15)을 따른다 |
| eyel2sdk 예제 `svmdemo_core` | svmdemo 와 같은 차 그림 | svmdemo 와 함께 |
| ltxm | 청크 입출력 사본(`ltxm_texmap`), 편집 화면 | P4. lbx 청크 입출력으로 바꿔 사본을 없앤다 |

이관 기간에 옛 API 를 남겨야 하면 lbsvm-core 에 "래티스 메시를 지금 draw list 에 넘기는" 얇은 층만 두고,
lbx-gl 에는 새 코드를 넣지 않는다.

## 12. 결정할 것

1. **용어**: 리그·조인트·래티스·컨스트레인트·공간·제어선(외곽/핀/슬라이스선)·칸·프로파일·경로 매개변수(§14).
2. **표기**: 핀 `p`, 슬라이스선 `s`. 옛 `f`·`b` 는 읽기만.
3. **슬라이스선 소속 규칙**(§4-3): 1개일 때 가까운 핀, 맞닿음은 같은 자리 두 개, 3개 이상은 오류.
4. **모듈**: `lbx_lattice` 를 lbx-geo 안에 둘지, 새 모듈로 둘지.
5. **식 문법 범위**: §6-3 정도로 시작해도 되는지.
6. **고정 영역 배율 기본값**: `pins` / `cross` / 수치.
7. **줄어들 때 규칙**: 고정 영역 비례 축소 + 경고가 기본으로 맞는지.
8. **래티스 저장**: PNG 청크 유지(그림 한 파일) / 사이드카 JSON(버전 관리·비교가 쉬움).
9. **컨스트레인트 저장**: 차종 컨스트레인트를 저장 체계 통일 스키마의 차량 문서에 넣을지.
10. **SWEEP u 기준**: u 를 무엇의 이동 거리로(범퍼 중앙이 S3000ABR 과 같다). 차 밑 구간 표현(§8-3).
11. **가이드 맵 그룹·메모리**: 그룹 단위 맵, 켜진 그룹만 굽기(맵 2~3장 돌려 쓰기), 텍셀당 mm 목표로 크기 정하기,
    단일 유닛 일정 곡률이면 맵 없이 셰이더에서 극좌표로 푸는 방법(해석적 데칼)을 함께 둘지.
12. **레벨 2(래티스 노드)**: 언제 넣을지.
13. **이관 중간층**: S3000ABR 이 옮겨 오기 전까지 옛 `TGlyph` 용법을 lbsvm-core 의 얇은 층으로 받쳐 줄지(§11-4).
14. **선의 샘플링 성질**(§16): 이음선(soft)·내용 경계선(hard)을 선 성질로 둘지, 저장 때 자동 판정해 힌트로 둘지,
    공간별 기본값(SWEEP hard, RECT·BODY soft)을 둘지.
15. **래티스 형식 개정**(§17): 반전 금지, 구간 성질(fix/str) 직접 기록, 자유 태그 핀, 같은 픽셀 위 래티스 여러 개를
    채택해 §4 의 슬라이스선 소속 규칙과 §6-1 형식을 대체할지.

### 15-1. 다른 모델(GPT)의 검토 의견

프로님이 같은 문제를 GPT 에게 물어 받은 의견이다. 요지는 "격자를 공통 데이터로 두고 용도별 의미를 그 위에 얹되,
세 기능(9-slice·길이 리그·가이드)을 처음부터 한 규칙으로 완전히 합치지는 않는다"였다.

받아들일 만한 지적:

| 지적 | 메모 |
|---|---|
| 고정·늘림을 핀·슬라이스선 소속에서 추론하지 말고 **구간 성질을 직접 기록** | 초안 2 의 예제를 따져 보다 추론 규칙을 두 번 고쳤다(1개일 때 소속, 고정 폭 0). 추론은 예외가 계속 생긴다 |
| **고정 배율과 전체 배율을 구분**. 핀 사이 배율을 고정 구간에 자동 적용하지 않음 | 초안 2 의 기본값 `pins` 는 UI(DPI 로만 커져야 함)에서 틀린다 |
| 길이가 남는데 늘릴 구간이 없으면 `cannot_fit`, 줄였으면 `compressed` **상태 반환** | 초안 2 에 없던 경우 |
| **핀 = 목표가 실제로 지정된 선**. 이름만 있고 바인딩이 없으면 일반 선 | "컨스트레인트 없는 핀", "암묵 핀" 해석이 필요 없어진다 |
| 문자열 식 대신 **구조화된 참조**(조인트·오프셋·단위·보간). 편집기에서만 식처럼 표시 | lbx-geo 에 파서를 넣지 않아도 되고 검증이 쉽다 |
| 잘못된 핀은 버리지 말고 **진단을 반환** | 초안 2 의 "어긋난 컨스트레인트를 버린다"는 모양이 몰래 바뀌는 동작이다 |
| 칸 자동 판정은 **캐시·힌트**. 불투명 칸이라도 블렌딩 여부는 재질·그리기 상태(전체 알파 곱 등)를 보고 렌더러가 결정 | 3D 바퀴 궤적의 알파 0.7 처럼 텍스처가 불투명해도 블렌딩이 필요한 경우가 있다 |
| 옛 데이터는 **용도별 어댑터**. 어느 용도로 읽었는지 기록, 원본 자동 덮어쓰기 금지, 스키마 버전, PNG 청크와 사이드카가 둘 다 있을 때 어느 쪽이 기준인지 명시 | 변환표에 빠져 있던 운영 규칙 |
| **기존 동작의 기준 출력**(대표 입력과 출력 좌표, 화면)부터 저장하고 시작 | — |
| SWEEP 에 거리 기준점, 후진 부호, 소속 유닛 좌표계, 경로 표본 부족 처리, 차 밑 구간 표현을 명시. 기존 DPGL 과 S3000ABR 을 각각 재현한 뒤 공통화 | — |

생각이 조금 다른 점:

- GPT 설계도 데이터 형식과 1차원 풀이·참조 형식은 하나다. 공간마다 목표 좌표를 만드는 방법이 다른 것은 초안도
  같다. 방향이 다르다기보다 통합 지점을 더 정확히 말한 것으로 본다.
- 배율을 늘 명시하게 하면 지정할 것이 늘어난다. 래티스가 자기 설계 배율(몇 mm/px 로 그렸는가)을 디자인 정보로
  갖고, 공간은 DPI 같은 배수만 주는 방법이 있다. S3000ABR 처럼 가이드 머리 길이가 띠 폭을 따라가는 경우는 SWEEP
  호출부가 배율을 계산해 넘길 수 있다.

### 15-2. 선 중심과 구간 중심

- 초안이 선 중심이 된 것은 옛 데이터 형식(선 위치 배열 + 선에 붙은 태그)과 편집기 코드, `b`·`f` 의 원래 뜻에서
  출발했기 때문이다. GPT 는 기존 코드를 보지 않고 문제에서 출발해 구간이 먼저 보였을 것이다(프로님 관찰).
- 층이 다르다고 볼 수 있다. **편집은 선 중심이 자연스럽고**(그림 위에서 선을 긋고 옮긴다), **저장은 선과 구간을
  함께 적는 쪽이 명확하다**(선 n 개, 구간 n−1 개). CSS Grid 의 "이름 붙은 선 + 구간 크기 규칙"이 같은 구조다.
- 그렇게 보면 슬라이스선 규칙(§4)은 저장 의미가 아니라 편집기가 구간 열을 채우는 기본 동작이 된다.

### 15-3. 핀은 선이다

- 구간 중심으로 편집해도 핀을 구간의 어디에 붙일지가 남는다. 구간 중심(`center`)은 축이 고정 구간 한가운데 있을
  때만 맞고(길이 리그는 `zone_f ≠ zone_b`), 비율로 적으면 구간을 고칠 때 어긋나고, 배치 쪽 오프셋으로 보정하면
  그림에 관한 사실이 배치로 새어 나간다.
- 그래서 **선 = 위치, 구간 = 성질, 이름 = 선**으로 나누는 안이 나왔다. 양옆 성질이 다른 선은 경계선, 같은 선은
  마커선이다. 핀은 이름 붙은 선이며 둘 중 어느 것이어도 된다. 고정 구간 안의 핀은 구간을 "고정 + 고정"으로 나누고
  풀이 결과는 같다.

  | 경우 | 적는 법 |
  |---|---|
  | 축(앞뒤 고정 폭이 다름) | 고정 · [축 핀] · 고정 |
  | DPGL 거리 표시 | 늘림 · [핀] · 늘림 |
  | 그림자 + 맞춤 | 고정(그림자) · [맞춤 핀] · 고정(모서리) · 늘림 … |
  | 버튼 가운데 아이콘 | 늘림 · 고정(아이콘) · 늘림, 핀 없음 |

- "축 핀을 옮기면 둘레 고정 구간도 같이 움직여야 한다"는 걱정은 디자인 편집에서는 필요 없다. 핀 위치(그림 속 바퀴
  중심)와 고정 구간 끝(펜더 그림이 끝나는 곳)은 별개의 사실이다. 실행 중에 고정 영역이 핀과 함께 놓이는 것은
  풀이가 한다.

### 15-4. 편집 흐름 (프로님 구상)

1. PNG 를 열고 쓸 영역 전체를 사각형으로 고른다. 기본은 전부 늘림.
2. 가로·세로 선을 그어 나눈다. 늘림은 선 수와 상관없으므로 여전히 전부 늘림.
3. 9-slice 는 선을 축마다 두 개 긋고, 생긴 칸(모서리)을 골라 고정으로 바꾼다. 분리형 구조라 그 칸의 가로 구간과
   세로 구간이 고정이 되어 9-slice 가 그대로 나온다.

메모:
- 칸 하나를 바꾸면 그 행과 열 전체가 바뀐다. 적용 전에 십자 모양으로 영향 범위를 보여 주고, 축 띠에서 구간 하나만
  바꾸는 조작도 둔다.
- 칠하기 방식(9-patch 처럼 축 띠에 성질 붓으로 칠하면 성질이 바뀌는 곳에 경계선이 생김)과 핀 도구(축 띠 위에 핀을
  떨어뜨리고 이름을 붙임, 경계선에 스냅)를 함께 두는 안도 나왔다.
- 틀(단순 / 9-slice / 9-slice + 아웃셋)에 여백 수치만 넣어 구간을 만드는 조작으로 옛 세 단계의 간편함을 살린다.

### 15-5. 선 순서와 방향

- 지금 형식은 배열 순서가 위치와 방향을 함께 나타낸다(`"x":[0,w],"y":[h,0]` 처럼 거꾸로 적어 반전, `TGlyph` 는
  `boundary.left > right` 로 배율 부호를 뒤집음). 그래서 DPGL 역상처럼 선 순서가 결과에 영향을 준다.
- 분리안: **선은 항상 픽셀 좌표 오름차순**으로 저장하고, **방향은 래티스 속성 하나**(회전 4 × 반전 2 = 8가지)로
  둔다. 지금 편집기의 `axis_types`(`0, 90, 180, 270, -0, -90, -180, -270`)가 그 8가지다. 방향은 그림을 그린 쪽이
  아는 사실이므로 디자인 정보다.
- 핀 목표 값이 방향과 맞지 않으면 진단으로 알린다. 편집기는 지금의 L 화살표처럼 목표 축 방향을 그림 위에 보여 준다.
- DPGL 폭 방향 `"center"` 반사는 방향이 아니라 디자인 방식(반쪽만 그리고 대칭으로 채움)이므로 별도 속성으로 둔다.

### 15-6. 기존 편집기 구조와 바꾸기 어려움

`tool/ltxm/src/ltxm_grid.cpp`(svmdemo 사본 `svmdemo_grid.cpp` 와 거의 같음)는 선 중심으로 설계돼 있다.

- 선 배열을 고치는 곳: 그리드 전체 이동, 크기 조정(`Resize`), 선 하나 끌기, 개수 바꾸기
  (`redistributeGridWithSegmentInterpolation`, `createUniformGrid`). 선을 하나씩 넣고 빼는 조작은 없다.
- 태그는 선마다 텍스트로 고친다.
- 데이터 조작과 ImGui 그리기가 한 파일에 섞여 있다(`HandleGridInteraction`, `RenderGridOverlay` 가 뷰어 상태를 직접 받음).

구간을 덧붙이는 방법(안):
- 구간 열(n−1)을 선 배열 옆에 두고, 선이 바뀔 때마다 재매핑 함수 하나를 부른다. 새 구간마다 중점이 옛 배치의 어느
  구간에 있었는지 보고 성질을 물려받는다. 기존 조작 코드의 로직은 그대로 둘 수 있다.
- 구간 고르기는 기존 히트 테스트(`ScanCoordinates`)로 "두 선 사이"를 찾는다.

어려운 곳:
1. 방향이 선 순서에 들어 있다(`check_axis_flipped_and_calc_range`, `axis_table`, L 화살표). §15-5 의 분리는 화면
   표시와 결과에 바로 닿는다.
2. 데이터 조작과 그리기가 섞여 있어, 바꾸기 전에 `VarRef` 만 받는 순수 함수부터 떼어 두는 편이 안전하다.

단계안(안):

| 단계 | 편집기 | 저장 |
|---|---|---|
| 1 | 지금 그대로 선과 태그로 편집 | 저장할 때 태그에서 구간 열을 계산해 함께 씀. 추론은 편집기·변환기 안에만 |
| 2 | 구간 클릭·칠하기, 칸 선택으로 고정, 재매핑 함수 | 구간 열을 직접 편집 |
| 3 | 방향을 선 순서에서 분리(8가지 값) | 선은 항상 오름차순 |

1단계만으로도 런타임 쪽(풀이·공간)은 명시적 구간 데이터로 시작할 수 있다.

### 15-7. 선례

조각마다 오래 다듬어진 툴·형식이 있다. 다만 네 가지를 한 뼈대(차량 스펙)에 묶은 것은 찾지 못했다(확인한 범위:
작성자가 알고 있는 내용, 문서로 다시 확인하지 않음).

| 조각 | 툴·형식 |
|---|---|
| N-slice 그림 | Android 9-patch(늘림 구간을 칠함, 여러 구간), CSS `border-image`·CSS Grid(이름 붙은 선 + 구간 규칙), Aseprite Slices(이름 붙은 사각형 + 9-slice + 피벗), Unity·Godot 9-slice |
| 그림을 뼈대에 붙여 변형 | Spine, DragonBones, Unity 2D Animation, Live2D Warp Deformer(격자 제어점), Puppet 도구(핀) |
| 경로를 따라 쓸기 | Unity LineRenderer·TrailRenderer(Stretch / Tile / RepeatPerSegment), Unreal Spline Mesh, Blender Curve + Array, Spine Path Constraint |
| 3D 메시 부분 늘리기 | Blender·Maya Lattice, Hook·Cluster |

툴을 들여오기는 어렵다. 엔진에 묶여 있거나(Unity·Unreal·Godot), 런타임 라이선스와 시간 애니메이션 모델이
걸리고(Spine), 지면 가이드를 맵에 굽는 부분은 어디에도 없다. 대신 저장 형식은 CSS Grid, 편집은 9-patch 칠하기와
Aseprite 식 이름 붙은 슬라이스, 경로 텍스처 모드는 LineRenderer 를 본뜨는 안이 있다. 디자이너가 Aseprite 를
쓴다면 ltxm 이 Aseprite 슬라이스 JSON 을 읽는 길도 생각해 볼 수 있다.

### 15-8. ltxm 의 제약과 미리보기

- **ltxm 은 엔드유저에게까지 배포된 툴이다.** 편집기 구조나 저장 형식은 충분히 검토한 뒤에만 바꾼다. 바꾸게 되면 옛 형식
  읽기·쓰기를 유지하는 방법과 배포 절차를 먼저 정한다.
- **미리보기 기능이 있어야 한다**(프로님). 디자인만 보고는 결과를 알 수 없다. 나온 안:
  - 대상 크기를 바꾸는 슬라이더(UI 그림), 차종 선택(차 그림·메시), 조향·진행 거리(가이드)
  - 풀이 상태(`compressed`·`cannot_fit`)와 진단을 구간 위에 표시
  - 차종 컨스트레인트 파일 하나를 미리보기 대상으로 열어 두기
- 미리보기를 ltxm 에 넣을지, 별도 툴로 둘지, svmdemo 쪽 창으로 둘지는 정하지 않았다.

### 15-9. 열린 질문

1. 저장 데이터에 구간 성질을 직접 적을지(§15-1·§15-2), §4 추론 규칙을 저장 의미로 둘지.
2. 핀을 선으로만 둘지(§15-3), 구간 이름 지점(`start`/`center`/`end`)도 허용할지.
3. 고정 배율을 래티스의 설계 배율 + 공간 배수로 나눌지(§15-1).
4. 방향을 선 순서에서 떼어 8가지 값으로 둘지, 그때 옛 자산 변환을 어떻게 검증할지(§15-5).
5. 편집기 단계안(§15-6)의 순서, 그리고 배포된 ltxm 을 언제·어떻게 바꿀지(§15-8).
6. 미리보기를 어디에 둘지(§15-8).

## 16. 키 경계 샘플링과 길이 리그 (2026-10-28)

DPGL 가이드를 보다가 찾은 원인을 정리하고, 같은 구조가 3D 길이 리그(`LB_LENGTH_RIG`)에도 있다는 점을 적는다.
결정이 아니라 분석이며, 초안 3 에서 §4·§5·§9 에 반영할지 검토한다.

### 16-1. 계기: 한쪽만 번지는 가이드

car.png 의 DPGL 격자(512×512 아틀라스)는 폭 방향 키가 다음과 같다.

| 폭 키 | 0 | 100 | 500 | center |
|---|---|---|---|---|
| 텍셀 y | 504 | 496 | 488 | 484 |
| 다음 구간 mm/텍셀 | 12.5 | 50 | (W/2 − 500)/4, 차폭 1.9~2.4 m 면 약 110~175 | — |

키는 텍셀 경계에 정확히 놓여 있다. 그런데 화면에서는 ㄴ자 발의 안쪽 끝(500 경계)만 80~110 mm 번지고, 바깥 끝은
선명했다.

원인은 다음과 같다.
- 이중선형 필터는 경계에서 ±0.5 텍셀에 걸쳐 섞는다. 알파 0.5 지점은 키 위에 정확히 온다.
- UV 는 키 사이를 구간별 선형으로 잇는다. 그래서 키에서 mm/텍셀(구간 배율)이 끊기고, 반 텍셀이 바닥에서 몇 mm 인지는
  양옆 구간이 따로 정한다.
- 500 경계의 색 쪽(100→500)은 반 텍셀이 25 mm 이고, 투명 쪽(500→center, 4 텍셀)은 55~90 mm 이다.
- 바깥 끝은 메시가 끝나는 기하 경계라 선명하다.

같은 계산으로 초록 긴 띠의 먼 끝(−2900→−1100, 225 mm/텍셀)과 ㄴ자 꺾인 안쪽도 약 110 mm 번진다. 길이 방향의
`-1100`/`-1099` 키는 4 텍셀을 1 mm 에 몰아넣은 손 가드로, 이 현상을 한쪽에서 막고 있던 장치다.

굽기 FBO(약 2 mm/px)와 디칼 샘플링은 원인이 아니다. 아틀라스를 읽는 첫 단계에서 생긴다.

### 16-2. 현행 처리: 자동 가드

lbsvm-core `TLBBand::GuardKeyEdges(eps)`(2026-10-28, 미커밋)가 격자를 읽을 때 키 경계를 자동으로 선명하게 만든다.

- **보통 키**: 반 텍셀이 바닥 위로 eps(0.5 mm)보다 길게 늘어나는 쪽에만, 키 ± eps 자리에 키에서 반 텍셀 떨어진
  텍셀을 가리키는 가드 키를 넣는다. 램프가 2·eps 폭으로 접힌다.
- **반 텍셀**로 넣으므로 손 가드(1 텍셀)와 달리 이웃 구간의 텍셀을 잃지 않는다.
- **끝 키·접힘 키**(양옆 구간이 텍셀에서 같은 쪽으로 가는 키, 좌우 대칭의 `center`)는 가드 대신 키 자체를 반 텍셀
  안으로 당긴다. 격자 밖 아틀라스 텍셀이나 접힌 반대편을 섞지 않는다.
- 1 텍셀 미만이거나 2·eps 보다 짧은 구간에는 가드를 넣지 않는다(손 가드와 충돌하지 않는다).
- 격자에 `"edge": "soft"` 가 있으면 옛 동작이다.
- `TLBBand` 단계에서 처리하므로 옛 GL 렌더러와 gfx 가이드 맵에 똑같이 적용된다. svmdemo 탑뷰·후방 단일 카메라에서
  두 경로 모두 번짐이 사라진 것을 확인했다(PC Debug). 리눅스·보드는 확인하지 않았다.

부작용: 키를 가로지르는 그라데이션은 키에서 계단이 된다. 가드 구간은 축소 샘플링이 되므로 아틀라스에 밉맵이 있으면
키 자리에 가는 줄이 생길 수 있다(지금 아틀라스에서는 보이지 않았다).

### 16-3. 길이 리그와 같은 구조

길이 리그도 매듭에서 기울기가 끊기는 구간별 선형 매핑이다. 두 기능은 같은 1차원 풀이의 결과를 쓴다.

| | DPGL 띠 | 3D 길이 리그 |
|---|---|---|
| 매핑 | 키: mm ↔ 텍셀, 구간별 선형 | 매듭: `y_in` → `y_out`, 구간별 선형 |
| 끊기는 것 | 구간 배율(mm/텍셀) | 늘림 배율 k |
| 원천의 이산 단위 | 텍셀(필터 폭 ±0.5 텍셀) | 삼각형(정점 사이는 선형) |
| 키에 걸친 단위 | 텍셀 하나가 양쪽 배율로 따로 늘어나 비대칭으로 번진다 | 매듭에 걸친 삼각형은 꺾이지 않는다. 실제 매듭이 가까운 정점으로 밀린다 |
| 키 위 공유 정점 | UV 하나로 양쪽 구간을 맡는다 | 노멀 보정 하나로 양쪽을 맡는다. `rig_map` 은 매듭 위 정점에 왼쪽 구간 기울기를 쓴다 |

전이 폭의 규칙도 같다. **원천 이산 단위 크기 × 그쪽 구간 배율**이다. DPGL 은 이웃 구간 배율 차이가 수백 배라 눈에
띄었고, 길이 리그는 늘림 배율이 1.0~1.3 정도라 같은 현상이 있어도 보이지 않는다.

### 16-4. 원하는 결과는 반대다

- **DPGL**: 키를 내용이 바뀌는 곳(색이 바뀌는 거리)에 두고, 구간 안은 단색으로 채운다. 키에서 **끊겨야** 맞다.
  가드는 키를 둘로 쪼개는 방법이다.
- **길이 리그·9-slice·차 그림**: 슬라이스선을 내용이 **이어지는** 곳(펜더가 끝나고 평평한 옆판이 시작되는 곳)에 두고,
  바퀴 아치 같은 특징은 고정 구간 안에 넣는다. 키에서 **이어져야** 맞다. 3D 표면은 매듭에서 실제로 꺾이지만(x 배율이
  갑자기 바뀐다), 정점 노멀 하나가 양쪽을 맡아 그 꺾임이 매끄럽게 감춰지고 그쪽이 보기에 낫다. 매듭에서 정점을 쪼개
  노멀을 따로 주면 DPGL 가드와 같은 일이 되어 꺾임이 드러난다.

§15-3 은 선을 양옆 구간 성질(고정·늘림)로 경계선과 마커선으로 나눴다. 여기에 축이 하나 더 생긴다.

| 선의 역할 | 놓는 자리 | 샘플링 | 예 |
|---|---|---|---|
| **이음선** | 내용이 이어지는 곳 | soft: 양쪽을 섞는다 | 9-slice 슬라이스선, 리그 고정 구간 끝, 차 그림 축 둘레 |
| **내용 경계선** | 내용이 바뀌는 곳 | hard: 가드로 쪼갠다 | DPGL 거리 키, 9-slice 테두리와 반투명 가운데 칸 사이 |

### 16-5. 설계에 반영할 점

1. **샘플링 성질은 칸 자동 판정(§5-2)과 같은 방식으로 정할 수 있다.** 저장할 때 선마다 양옆 텍셀을 비교해 어긋나면
   hard 를 힌트로 남긴다. 단색 그림에서는 hard 를 걸어도 양옆 색이 같은 자리는 계단 높이가 0 이므로, 행마다 내용이
   다른 DPGL 격자 전체를 hard 로 두어도 부작용이 없다. 피해를 보는 것은 키를 가로지르는 그라데이션뿐이다.
2. **§5-2 의 "가운데를 그리면 테두리가 늘림 배율만큼 번진다"가 이 현상이다.** 초안은 가운데 칸을 빈 칸으로 그리지 않는 방법으로 피했다. 반투명
   가운데 칸이 있는 액자(패널)는 빈 칸으로 풀리지 않으므로, 경계선을 hard 로 두어야 한다.
3. **가드는 풀이(§7) 뒤 메시 생성(§9)의 일이고, 원천이 래스터일 때만 뜻이 있다.** 판단에 쓰는 값(선 양옆 배율 × 반
   텍셀 > eps)은 풀이 결과로 이미 나온다. 그래서 RECT·BODY·SWEEP 어느 공간이든 같은 코드로 된다. 원천이 모델 mm 인
   3D 리그에는 해당하지 않는다.
4. **접힘 처리는 미러 대칭 베이킹의 이음매 문제와 같다.** `center` 를 반 텍셀 당기는 것은 대칭 반쪽 UV 섬에 거터를
   주는 것과 같은 일이다. 래티스의 `mirror` 속성이 이 처리를 함께 맡는다.
5. **3D 쪽에서 볼 것은 매듭 자리와 정점의 정렬이다.** 매듭에 걸친 긴 삼각형은 실제 매듭을 가까운 정점으로 밀어
   버리고, 로우폴리 메시는 삼각형이 커서 영향이 크다. 메시를 자르기보다 측정 도구가 `zone_f`/`zone_b` 를 가장 가까운
   에지 루프(같은 x 의 정점 무리)에 맞춰 주는 편이 원본 메시를 고치지 않는 원칙과 맞는다. 같은 이유로 코가 둥근 앞
   오버행 전체를 늘림 구간으로 두면 앞면 곡선이 변형되므로, 범퍼 핀 쪽에도 고정 구간을 두는 것이 이음선 원칙과 맞다.
6. **핀은 공유한다.** DPGL 길이 키 `"axle"`·`"0"`(뒤범퍼)와 리그의 `axle[i]`·범퍼 핀은 같은 BODY 조인트다. 지금은
   `LoadBandFromVariant(..., -overhang, width)` 처럼 인자로 따로 받는다. 축거·오버행을 리그로 바꾸면 가이드도 같은
   조인트를 따라와야 하므로, P2·P3 순서와 상관없이 조인트 조회 하나를 먼저 두는 것이 맞다.

정리하면 길이 리그와 DPGL 띠는 같은 1차원 풀이를 쓰고, 다른 것은 "끊김을 드러내는가, 감추는가"라는 선 성질 하나다.
그 성질은 저장할 때 자동으로 판정할 수 있으므로 통합을 막는 요소가 아니라 통합안의 항목 하나가 된다.

### 16-6. 열린 질문

1. 샘플링 성질을 선에 둘지, 칸 경계(칸 쌍)에 둘지. 행마다 내용이 다른 경우 선 하나에 hard 와 soft 가 섞인다.
   단색 그림에서는 선 단위 hard 로 충분하다(§16-5 1 항).
2. 공간별 기본값(SWEEP hard, RECT·BODY soft)과 자동 판정 중 무엇을 우선할지.
3. 가드 폭 eps 를 목표 단위 고정값(0.5 mm)으로 둘지, 굽기 해상도에 맞출지.
4. 리그 매듭을 에지 루프에 맞추는 일을 측정 도구에서 할지, `LB_LENGTH_RIG_Build` 에서 할지.

## 17. 래티스 형식 개정 방향 (2026-10-28 논의)

DPGL 격자를 트럭에 쓰려다 나온 논의를 정리한다. §4 의 "슬라이스선을 가까운 핀에 소속시키는" 추론 규칙과 §6-1 의
형식을 대체하는 안이다. 큰 방향은 합의했고, 세부는 §17-9 에 남긴다.

### 17-1. 계기

car.png 의 DPGL 격자는 승용차용이다. 거리 표시가 뒤범퍼에서 0.5·1·3 m 이고, 그 값이 그림 데이터(PNG 청크의
태그)에 직접 적혀 있다. 트럭이라면 같은 그림으로 1·3·10 m 에 표시하고 싶을 수 있다.

- 그림을 차종마다 고치는 방법도 있다(대개 한 차종에 대해 튜닝하므로). 그러나 asset 은 배포 고정 자산이고, 차종·기기에
  따라 바뀌는 값은 config 층에 두는 저장 원칙에 맞지 않는다.
- 모든 키를 비례로 늘리면 발 두께와 틈도 3~7배로 굵어진다. 경계만 옮기고 모양은 유지해야 한다.

### 17-2. 지금 격자 키의 성격

| 키(mm) | 실제 뜻 | 성격 |
|---|---|---|
| `0`, `-500`, `-1000`, `-3000` | 빨강·노랑·초록 구간의 경계 | 배치: 차종마다 바꾸고 싶은 값 |
| `-2900`, `-900`, `-400` | ㄴ자 발(가로 막대) 두께 100 mm | 디자인 |
| `-1100`, `-600` | 색 사이 틈 100 mm | 디자인 |
| `-1099` | 손으로 넣은 가드 | 자동 가드(§16-2)로 필요 없음 |
| `100`, `axle` | 차 밑 구간 | 조인트에 붙는 값 |

폭 방향은 `0`(옆면)·`center` 가 조인트, `100`(선 두께)이 디자인, `500`(발 길이)이 배치에 가깝다. 배치와 디자인이
한 배열에 섞여 있어 경계만 옮길 수 없다. 3D 길이 리그는 이미 둘을 나눠 두었다(모델 메시의 measure 블록 = 디자인,
VEH_SPEC 의 축 위치 = 배치).

### 17-3. 전제: 반전 금지

지금 형식은 `"x": [0, w]` 와 `"x": [w, 0]` 처럼 선 배열의 순서로 반전을 나타낸다(§15-5). 이 때문에 "구간 i = 선 i 와
선 i+1 사이"가 가리키는 픽셀 범위가 방향에 따라 바뀌고, 구간 성질은 선 배열과 함께 뒤집어야 하며, 에디터에서 구간을
골라도 방향을 알아야 번호가 정해진다. 지금까지 선 중심으로 설계할 수밖에 없었던 이유가 이것이다.

**반전을 금지한다.** 선은 항상 픽셀 오름차순으로 저장한다. 구간 i 는 언제나 `px[i]..px[i+1]` 이고, 구간 성질은 그림에
고정된 사실이 된다. 반전이 하던 일은 다음이 나눠 맡는다.

1. **배치 방향은 연결 값이 정한다.** 핀 목표가 픽셀 순서와 반대로 줄어들면 풀이가 축을 뒤집어 놓는다(§7-1). 계산
   결과이고 저장하지 않는다. RECT 의 9-slice 도 `start → right`, `end → left` 로 연결하면 좌우가 뒤집힌다.
2. **대칭도 붙이는 방식이다.** 지금 격자의 `center` 반사는 디자인 속성이 아니라 "반쪽 그림을 양쪽에 붙인다"는 배치다.
   방향을 연결 값이 정하므로, 같은 래티스를 왼쪽(`side → side.left`, 차 안쪽으로 증가)과 오른쪽(`side → side.right`,
   반대로 감소)에 한 번씩 붙이면 반사가 된다. 래티스에는 미러선을 두지 않는다. 좌우를 다르게 붙이는 경우(비대칭
   가이드)도 같은 방식이라 따로 장치가 필요 없다. UI 는 "대칭으로 붙이기" 같은 편의 조작으로 두 배치를 한 번에 만든다.
   디자이너가 반사를 의도하지 않은 그림이라도 반사해 붙이는 편이 보기 좋으면 그렇게 쓸 수 있다. 반사가 그림의
   속성이었다면 이런 선택이 막힌다.

**원칙: 개별 요소를 단순하게 둔다.** 래티스는 그림에 관한 사실(선 위치, 구간 성질, 태그)만 갖고, 방향·반사·몇 번
붙이는가처럼 "어떻게 붙이는가"는 전부 연결(배치)이 정한다. 요소마다 할 일이 하나뿐이어야 조합이 자유롭고, 한 요소를
바꿔도 다른 요소가 흔들리지 않는다.
3. **가로·세로 교환은 축 지정으로 한다.** 축 이름을 `lon`/`lat` 로 두고, 각 축이 텍스처의 `x`/`y` 중 어느 것인지
   적는다. 옛 `"axis": 1` 이 이것으로 바뀐다.

### 17-4. 선·구간·태그

- **선**은 위치만 갖는다(픽셀 오름차순).
- **구간**(이웃 선 사이, 선이 n 개면 n − 1 개)이 성질을 갖는다. `fix`(모양 유지) 또는 `str`(늘림). 반복(§6-1 의
  `repeat`)도 같은 자리에 둔다.
- **핀**은 태그가 붙은 선이다. 태그 이름은 에디터에서 자유롭게 붙이고(`danger`·`warn`·`safe` 등), 뜻은 연결(§17-7 ②)이
  정한다. 색 이름보다 뜻 이름을 권한다(같은 배치에 다른 색 디자인을 얹을 수 있게).

**풀이 규칙은 하나다.** 연결된(목표 값이 있는) 이웃 핀 A·B 사이에서 `fix` 구간은 원천 길이 × 축척(× 배율 k)을
유지하고, `str` 구간들이 남는 길이를 원천 길이 비율로 나눠 갖는다.

- 슬라이스선이 어느 핀에 속하는지 묻지 않는다. **핀에 맞닿은 연속된 `fix` 덩어리가 그 핀과 함께 움직인다.**
- 양옆이 `str` 인 `fix` 구간(가운데 눈금 등)은 두께를 유지한 채 양옆 `str` 의 원천 비율 자리에 뜬다. 정확한 거리에
  두려면 그 선에 태그를 달아 핀으로 만든다. 선 개수에는 제한이 없다.
- 경계 사례는 규칙이 아니라 진단으로 처리한다.
  - 두 핀 사이에 `str` 이 없는데 목표 길이가 `fix` 합과 다르면 맞출 수 없다. 길면 `cannot_fit`, 짧으면 고정 구간을
    비례로 줄이고 `compressed` 를 돌려준다. 에디터 미리보기가 그 구간을 표시한다.
  - 가장 바깥 핀의 바깥은 기준이 없으므로 `seg` 값과 상관없이 고정이다(아웃셋).
  - 연결되지 않은 핀은 보통 선이다.
- 에디터 기본값은 전부 `str` 이다. 구간을 클릭하거나 축 띠를 칠해 `fix` 로 바꾼다(§15-4).

§15-1 의 지적(고정·늘림을 추론하지 말고 구간 성질을 직접 적는다)과 §15-2·§15-3 의 "선 = 위치, 구간 = 성질, 이름 =
선"을 그대로 채택한 것이다. §15-9 열린 질문 1 의 답이 된다.

### 17-5. 예: 같은 텍스처, 두 가지 디자인

노랑 부분(-1000 ~ -500)만 본다. 텍스처와 선은 같고 구간 성질만 다르다.

**A. 사이드 라인이 길게 이어지는 디자인.** -900 은 -1000 핀의 고정 영역(발), -600 은 -500 핀의 고정 영역(틈)이고,
그 사이 노랑 몸통이 늘어난다.

```json5
"px":  [32,     40,    48,    56],
"tag": ["warn", null,  null,  "danger"],
"seg": [  "fix",  "str",  "fix"  ]      // 발 100 · 노랑 몸통 · 틈 100
```

**B. 사이드 라인을 핀에서 400 mm 로 짧게 고정하는 디자인.** -900 과 -600 이 둘 다 -1000 과 함께 움직이고 틈이
늘어난다.

```json5
"px":  [32,     40,    48,    56],
"tag": ["warn", null,  null,  "danger"],
"seg": [  "fix",  "fix",  "str"  ]      // 발 100 · 노랑 몸통 300 · 틈
```

| 선 | 승용차 A (warn 1000, danger 500) | 승용차 B | 트럭 A (warn 3000, danger 1000) | 트럭 B |
|---|---|---|---|---|
| warn (32) | -1000 | -1000 | -3000 | -3000 |
| 발 끝 (40) | -900 | -900 | -2900 | -2900 |
| 노랑 끝 (48) | -600 | -800 | -1100 (몸통 1800 mm 로 늘어남) | -2800 (몸통 100 mm 유지) |
| danger (56) | -500 | -500 | -1000 | -1000 |

`fix` 구간의 길이는 원천 px × 축척(12.5 mm/px)이다. 지금 그림의 노랑 몸통은 8 px 이라 B 에서 고정하면 100 mm 가 된다.
사이드 라인을 400 mm 로 짧게 고정하려면 그림에서 몸통을 24 px 로 그리거나, 그 래티스의 `fix` 축척을 키운다.
§4-3 의 "가까운 핀" 규칙으로는 B 를 나타낼 수 없다(-600 은 -500 에 더 가까워 늘 -500 에 붙는다).

> 정정(2026-10-29): 처음 판의 표는 B 의 몸통이 명목 길이 300 mm 를 유지한다고 보고 -2600, 기본값에서 A·B 가 같다고
> 적었다. 축척이 하나인 형식에서는 위 표가 맞다(ltxm `--selftest` 로 확인).

### 17-6. 같은 픽셀 위의 래티스 여러 개

A/B 의 선택은 "늘어날 때 어떻게 보여야 하는가"라는 그림 쪽 의도다. 그래서 연결에서 `seg` 를 덮어쓰지 않고, **같은
텍스처 영역에 래티스를 여러 개** 둔다(`dpgl_long`, `dpgl_short`). 래티스는 "텍스처 영역 + 선 + 구간 성질 + 태그" 한
묶음이고, 픽셀은 한 벌을 공유한다. ltxm 에서 래티스를 복제해 `seg` 만 바꾸고, 쓰는 쪽은 글리프 목록에서 고른다.
9-slice 그림을 늘림 방식만 달리해 두 번 쓰는 경우도 같다.

### 17-7. 데이터 세 덩어리

**① 래티스**(ltxm 이 편집, PNG 청크, 배포 고정). 지금 car.png 의 텍스처 위치를 그대로 쓴 예:

```json5
"lattices": {
  "dpgl_basic": {
    "rect": [8, 484, 88, 504],          // 아틀라스 안 영역(px)
    "mm_per_px": 12.5,                  // 그릴 때의 기준 축척 → fix 구간의 mm 크기
    "lon": {                            // 길이 방향(px 가 작을수록 차에서 멂)
      "axis": "x",
      "px":  [8,      16,    24,    32,     40,    48,    56,       64,    72,      88],
      "tag": ["safe", null,  null,  "warn", null,  null,  "danger", null,  "start", "axle"],
      "seg": [   "fix", "str", "fix", "fix",  "str", "fix", "fix",    "str", "str"   ]
      //       safe 발  초록  warn 틈 warn 발 노랑  danger 틈 danger 발 빨강  차 밑
    },
    "lat": {                            // 폭 방향
      "axis": "y",
      "px":  [484,     488,    496,  504],
      "tag": ["inner", "foot", null, "side"],
      "seg": [   "str",   "str",  "fix"  ]    // 투명 · 발 나머지 · 선 두께 100
    },                                  // 반쪽 그림 — 좌우는 연결에서 두 번 붙인다
    "defaults": {                       // 디자이너가 의도한 기본 배치(가장 아래 층)
      "lon": { "start": 0, "danger": 500, "warn": 1000, "safe": 3000 },
      "lat": { "foot": 500 }
    }
  }
}
```

**② 연결**(svmdemo UI 에서 정하고 config 층에 override-only 로 저장). UI 에서 글리프(래티스) 목록 중 하나를 고르면
그 래티스의 태그가 축별로 나열되고, 태그마다 무엇에 연결할지 정한다. 고를 수 있는 것은 공간(§8)이 제공하는 조인트
(SWEEP 이면 `rear_bumper`·`axle`·`side.left`·`side.right`·`center`)와 거리 입력, "기본값"이다. 고정 구간 배율 k 도
축별로 준다. 좌우 대칭 가이드는 같은 래티스를 두 번 붙인 것이다(§17-3 2 항).

```
[가이드: rear_dynamic]   글리프 [car.png#dpgl_basic ▼]   붙이기 [대칭(좌·우) ▼]
 길이 축   start  → [조인트 ▼ rear_bumper]
           danger → [거리 ▼ 1000 mm]
           warn   → [거리 ▼ 3000 mm]
           safe   → [거리 ▼ 10000 mm]
           axle   → [조인트 ▼ axle(fixed)]
 폭 축     side   → [조인트 ▼ side]            (대칭이면 왼쪽 side.left, 오른쪽 side.right)
           foot   → [기본값(500) ▼]            (side 에서 차 안쪽으로)
           inner  → [조인트 ▼ center]
 고정 구간 배율  길이 [1.0]  폭 [1.0]
```

저장되는 것은 기본값과 다른 것만이다. 트럭 차종 문서의 예:

```json5
"guides": {
  "rear_dynamic": {
    "glyph": "car.png#dpgl_basic",
    "attach": "symmetric",              // 좌·우 두 배치를 만든다(기본값이면 생략)
    "lon": { "danger": 1000, "warn": 3000, "safe": 10000 }
  }
}
```

비대칭이 필요하면 `"attach": "symmetric"` 대신 배치를 둘 적고 각자 연결한다(예: 오른쪽만 발 길이 800).

저장 층은 저장 체계 통일 설계의 판정 규칙을 따른다. 거리 표시는 차종에 따라 다르므로 L2(차종), 제품 계열 기본값은
L1, 운전자가 고르게 한다면 U 다. asset 의 `defaults` 가 가장 아래 층이다. 키는 키 사전에 `guide.*` 로 등록한다.

**③ 풀이 결과**(코드가 만들고 저장하지 않음). TLBBand 키의 mm 값이며, 띠·자동 가드·가이드 맵 코드는 그대로 쓴다.

| px | 선 | 승용차(defaults) | 트럭 |
|---|---|---|---|
| 8 | safe | -3000 | -10000 |
| 16 | safe 발 끝 | -2900 | -9900 |
| 24 | warn 틈 끝 | -1100 | -3100 |
| 32 | warn | -1000 | -3000 |
| 40 | warn 발 끝 | -900 | -2900 |
| 48 | danger 틈 끝 | -600 | -1100 |
| 56 | danger | -500 | -1000 |
| 64 | danger 발 끝 | -400 | -900 |
| 72 | start | 0 | 0 |

승용차 열은 지금 격자 값과 같아 바꾸기 전과 화면을 비교할 기준이 된다. ㄴ자 모양은 길이 키 × 폭 키 격자 위에서
텍셀이 그대로 그린다. 발 두께는 길이 축의 `fix` 가, 선 두께는 폭 축의 `fix` 가 정하므로 핀마다 두께를 두 개씩 줄
필요가 없다.

### 17-8. 옛 격자 읽기(어댑터)

옛 `grids` 는 읽기만 하고 변환한다. 원본 PNG 는 덮어쓰지 않는다.

- 선 배열을 픽셀 오름차순으로 정렬하고, 거꾸로 적혀 있던 정보는 기본 연결의 방향으로 옮긴다.
- 옛 DPGL 숫자 태그는 명목 위치다. 태그 이름(`"-500"` 등)을 그대로 핀 이름으로 쓰고, 명목 값을 `defaults` 로 둔다.
  UI 에는 숫자 이름으로 보인다. 새 그림부터 `danger` 처럼 이름을 붙인다.
- `seg` 열은 변환할 때 한 번만 추론해 채운다. 배치 대상 핀(구간 경계)에 맞닿은 짧은 구간은 `fix`, 나머지는 `str`.
  어느 키가 배치 대상인지 옛 데이터에는 없으므로 변환기 설정으로 받는다(DPGL 은 `0`·`-500`·`-1000`·`-3000`).
  §4-3 의 "가까운 핀" 규칙은 이 변환기 안에서만 쓰고, 고정 구간이 핀 간격의 절반보다 길면 진단을 남긴다.
- `-1099` 같은 손 가드는 변환 때 없앤다(자동 가드가 대신한다).
- 옛 폭 태그 `center`(반사)는 래티스에서 없애고 기본 붙이기를 대칭(좌·우 두 배치)으로 둔다. `center` 선은 보통 핀
  (`inner`)이 된다.
- 옛 9-slice 의 `b`/`f`/`x` 는 §10-1 표대로 변환하되, `b` 는 슬라이스선이 아니라 그 바깥 구간의 `fix` 로 바뀐다.

### 17-9. 남은 문제

1. **색마다 선 두께를 배치에서 다르게 주기**(danger 만 150 mm). 폭 축은 모든 색이 공유하므로 분리형으로는 안 된다.
   색마다 띠를 따로 두거나(폭 축 정의만 공유), 그림 안에서 고정 구간 폭을 넉넉히 잡고 색별 두께를 텍셀로 그린다.
2. **먼 표시일수록 굵게 하기.** 발 두께는 길이 축의 `fix` 구간마다 배율 k 를 주면 된다. 선 두께를 거리에 따라
   키우는 것은 폭이 u 에 따라 변하는 것이라 분리형이 아니다(§6-5 래티스 노드나 테이퍼가 필요하다).
3. **`start` 의 기준.** 지금은 뒤범퍼이고 `rear_bumper` 조인트에 묶인다. S3000ABR 과 곡선 기준(범퍼 모서리 궤적과
   축 원호)을 맞추는 §12 10 항과 엮인다.
4. **붙이기 목록의 형식.** `"attach": "symmetric"` 같은 편의 값과 배치를 여러 개 적는 일반 형식을 어떻게 함께 둘지,
   그리고 UI 에서 비대칭 배치를 어떻게 보여 줄지.
5. **고정 구간 배율 k 의 기본값.** 래티스의 `mm_per_px`(설계 축척) × 공간 배수로 둘지(§15-1).
6. **svmdemo 연결 UI 의 자리.** 가이드 패널 안에 둘지, 차량 툴(Model Spec 창 계열)과 합칠지.
7. 이 개정을 채택하면 §4(제어선 규칙)·§6-1(형식)·§10(현행 기능 옮기기)을 초안 3 에서 다시 쓴다.
