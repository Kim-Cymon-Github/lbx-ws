# S3000ABR MCU 링크 CAN 수신량 분석 (2026-09-21)

## 1. 결론

- **앱(lbsvm-app 통신 경로)은 MCU 가 보낸 바이트를 하나도 잃지 않는다.** 커널 UART 수신량과 앱의
  `read()`·파서 입력·파서 소비량이 측정 오차 안에서 모두 같다. 체크섬·헤더 오류, 정체, 버림은 0 이다.
- 「앱이 CAN 프레임의 1/3 만 받는다」던 이전 판정은 **측정 해석 오류**였다. 원인은 7 절에 적는다.
- 버스 송신량보다 적게 들어오는 것은 유실이 아니라 **MCU 의 전달 규칙** 때문이다(5 절).
  - MCU 는 **페이로드가 바뀐 프레임만** 올려 보낸다. 같은 값이 반복되는 ID 는 올라오지 않는다.
  - policy 0x81 에서는 여기에 **전 ID 합산 약 100 frame/s 상한**이 더해져, 바뀌는 ID 가 많으면
    휠펄스까지 깎인다. policy 0xFF 에서는 상한이 없다.
- 이전에 「0x111 이 유실된다」고 본 것은 주입기가 0x111·0x52A 에 고정값을 보냈기 때문이다.

## 2. 수신 경로

| 단계 | 담당 | 비고 |
|---|---|---|
| 커널 tty | 16550A `/dev/ttyS3`, 1.5 Mbps | 수신 바이트는 `/proc/tty/driver/serial` 의 `rx:` |
| 읽기 | `ThreadTransport`(read_mode `thread`) 또는 `UvTransport`(`loop`) | 스레드 모드는 128 KB 링, uv 모드는 uv_pipe |
| 파싱 버퍼 | `ProtocolBuffer` 8 KB | 스레드 모드는 `fill()` 이 링에서 옮긴다 |
| 파싱 | `ProtocolHandler::drain` → `LBMCUParse` | `ProtocolSystem::update` 안, 메인 스레드 |
| 배달 | 리스너 → `LbMcuTriggerHandler` → `ECSWorld::emit` | entt 큐에 넣는다 |
| 소비 | `VehicleMotionSystem::on_can_frame` | 다음 iteration 의 `dispatcher().update()` 에서 |

파싱과 emit 을 메인 스레드에 둔 이유는 ECS(entt dispatcher)가 메인 전용이기 때문이다. 그 덕에 소비측
시스템들은 잠금 없이 이벤트를 받는다. 읽기만 스레드로 떼어낸 `thread` 모드는 고속 포트용으로 따로
마련돼 있다(`protocol_transport.h` 주석).

## 3. 측정 방법

- 주입: PC 의 CANable(slcan, COM3)로 0x2B0 100/s, 0x387 50/s, 0x111 100/s, 0x52A 10/s, 0x220 100/s.
  앱 필터는 0x2B0·0x387·0x111·0x52A 네 개다(0x220 은 기본 필터에 없다). 필터 대상 합계는 260/s 이다.
- 커널: 주입 중 `/proc/tty/driver/serial` 의 `rx:` 를 5 초 간격으로 두 번 읽는다.
- 앱: 임시 계수(현재는 제거했다)로 창마다 `read()` 바이트, `fill()` 바이트, `drain` 호출 수, 파서에
  넘긴 바이트, 파서가 소비한 바이트를 [박자] 로그에 찍었다.
- MCU 패킷(0x38 CAN_RX)은 DLC 5 기준 18 B 이고 한 패킷에 CAN 프레임 하나가 실린다.

## 4. 측정 결과 (thread 모드, policy 0x81)

| 단계 | 값 |
|---|---|
| 커널 수신 | 7,641 B / 약 5.2 s ≈ 1,470 B/s (약 82 패킷/s) |
| 앱 `read()` | 창 7개 합계 6,903 B / 4.87 s ≈ 1,420 B/s |
| `fill` = 파서 입력 = 파서 소비 | 창마다 `read()` 와 같은 값 |
| bad_ck · bad_hdr · stall · lost | 모두 0 |
| 0x387 도착 | 창(약 0.65 s)마다 30~37 개 ≈ 50/s |

policy 0xFF 에서도 커널 수신은 약 1,400 B/s 로 같았다. 커널과 앱의 차이 3 % 는 두 측정의 시작·끝
시점이 어긋난 데서 온 것이다.

## 5. MCU 의 전달 규칙

앱을 내린 상태에서 `/dev/ttyS3` 원시 바이트를 4 초 뜨고(`-ixon -ixoff` raw), 0x38 패킷을 CAN ID 별로
셌다. MCU 는 앱이 기동 때 걸어 둔 필터 4 개와 policy 를 그대로 들고 있다. 주입량은 0x2B0 100/s(사인
조향각, 0.1° 단위라 값이 바뀌는 것은 초당 약 30 번), 0x387 50/s(매번 바뀜), 0x111 100/s, 0x52A 10/s 다.

| 조건 | 0x111 | 0x2B0 | 0x387 | 0x52A | 합계 |
|---|---|---|---|---|---|
| policy 0x81, 0x111·0x52A 고정값 | 0 | 29.5 | 49.8 | 0 | 79 |
| policy 0x81, 0x111 매번 바뀜 | 38.0 | 25.2 | **37.8** | 0 | 101 |
| policy 0xFF, 0x111 매번 바뀜 | 99.8 | 29.5 | 50.0 | 0 | 179 |

(단위 frame/s. 0x111 을 바꿀 때는 기어 해석에 쓰지 않는 d2 바이트만 바꿨다.)

- **바뀌지 않는 프레임은 올라오지 않는다.** 두 policy 모두 같다. 0x2B0 도 수신 118 개 가운데 서로
  다른 값이 98 개로, 값이 바뀐 만큼만 왔다. 0x81 의 duty 쪽 주기 전송은 4 초 창 안에서 보이지 않았다.
- **policy 0x81 은 합계 약 100/s 에서 자른다.** 바뀌는 ID 가 늘자 휠펄스가 50 → 37.8/s 로 깎였다.
  0xFF 에서는 바뀐 프레임이 모두 올라왔다.
- XON/XOFF 는 원인이 아니다. 앱의 `UartDevice` 는 `c_iflag = IGNPAR` 로 통째 대입하고, 실행 중 보드
  `stty -a` 도 `-ixon -ixoff -ixany` 였다. 0x111 ID 바이트(0x11)가 든 패킷도 값이 바뀌면 정상 도착했다.
- 그 밖에 약 1 Hz 로 0x37 패킷(`80 00`)이 온다.

### 5.1 판단

- 실차의 SAS11(0x2B0)·TCU11(0x111) 등은 메시지 카운터·체크섬 필드가 있으면 매 프레임 값이 바뀐다.
  policy 0x81 이면 합계 100/s 상한에 걸려 **휠펄스가 깎일 수 있다.** 그래서 앱 기본값과 설정을
  svmdemo 와 같은 0xFF 로 바꿨다(2026-09-21).
- 기어처럼 오래 안 바뀌는 신호도 **앱 재시작 직후에는 온다.** 0x111 고정값을 계속 주입하는 중에
  앱을 다시 띄우자, 0x56 조회 없이도 0.23 초 만에 기어 D 를 받았다. 기동 때의 필터 재등록이 MCU 의
  「직전 전송값」 기억을 비우는 것으로 보인다. io-serial 주석의 「재시작하면 영영 모른다」와는 다르다.
- 그래서 io-serial 식 0x56 초기 조회·주기 폴링은 **넣지 않았다.** 남는 쓸모는 이벤트 유실 보정뿐인데,
  현재 부하(0xFF 에서 약 180 fr/s)는 io-serial 이 잰 MCU 처리 상한(약 660 fr/s)에 한참 못 미친다.
  문제가 생기면 그때 넣는다.
- 이전 svmdemo 측정(policy 0xFF, 165~196/s)이 앱보다 많았던 것도 policy 차이로 설명된다.

## 6. 구조 관찰

앱의 수신 경로 자체는 이번 부하에서 결함이 없다. 다만 동작을 이해하는 데 필요한 성질 두 가지를 적어
둔다.

### 6.1 이벤트가 들어오면 메인 루프가 프레임과 별개로 한 번 더 돈다

`SVMAppBase::run` 은 `uv_run(UV_RUN_ONCE)` 뒤 프레임 게이트를 평가한다. 카메라 세대(Barrier)나 바닥
주기(Floor)가 아니어도 **ECS 큐에 이벤트가 있으면 `ServiceKind::Bypass` 로 iteration 을 서비스**한다
(`SVMAppBase.cpp` 292 행 부근 주석, `frame_pacing.h`). 입력·전원·저장 통지를 다음 프레임까지 붙잡지
않으려는 의도이며, Bypass iteration 은 프레임 세대로 세지 않아 녹화 PTS 에 영향을 주지 않게 설계돼 있다.

그 결과 CAN 이 흐르는 동안에는 다음이 이어진다.

1. iteration N 의 `drain` 이 패킷을 파싱해 이벤트를 큐에 넣는다.
2. 읽기 스레드의 `uv_async_send` 가 `uv_run` 을 깨우고, 큐가 비어 있지 않으므로 iteration N+1 이
   Bypass 로 서비스된다.
3. N+1 에서 앞 이벤트가 배달되고 새로 도착한 패킷이 다시 파싱된다.

실측으로는 CAN 이 없을 때 약 30 Hz 이던 `update_all` 호출이 CAN 주입 중 약 86 Hz 로 늘었다. 패킷 수와
iteration 수가 거의 같아지는 것도 이 때문이다. 배달 지연은 짧아지는 대신 `dispatcher().update()` 와
`update_all` 이 입력 이벤트 속도로 돈다. 지금의 80 패킷/s 에서는 문제가 드러나지 않았으나, 입력 빈도가
훨씬 높은 장치를 같은 경로로 붙일 때는 이 비용(CPU 사용량)을 먼저 재 봐야 한다. 이번에는 CPU 사용량을
재지 않았다.

### 6.2 단계별 처리량은 로그로 바로 보이지 않는다

`uart stats` 콘솔 명령과 transport·parser 통계는 **오류와 유실**(bad_ck, bad_header, rx_stall,
rx_lost_bytes)을 센다. 정상 흐름의 바이트 수는 세지 않으므로, 「어디서 줄었나」를 가르려면 커널
카운터와 앱 쪽 수치를 따로 맞춰 봐야 한다. uv 모드의 유실이 커널 안에서 일어나 앱에 보이지 않는다는
점은 `protocol_transport.h` 에 이미 명시돼 있다.

## 7. 이전 판정이 틀린 경위

- [박자] 로그는 `VehicleMotionSystem::update` 60 회마다 한 줄을 찍는다. 이전 분석은 CAN 이 없을 때의
  간격(2.0 s, 30 Hz)을 창 길이로 고정해 놓고 초당 수신량을 계산했다.
- 실제로는 6.1 의 Bypass 때문에 CAN 이 흐르면 창이 0.65 s 로 줄어든다. 창 길이를 2 s 로 나눴으니
  수신량이 1/3 로 계산됐고, 「앱 프레임당 패킷 약 1 개」라는 겉보기 규칙도 여기서 나왔다.
- 교훈: 창 단위 계수는 **로그 타임스탬프로 실제 창 길이를 재서** 나눈다. 비율을 판정하기 전에
  커널 카운터와 같은 시간 구간으로 맞춘다.

## 8. 다음에 추적할 때

- 커널: `grep '^3:' /proc/tty/driver/serial` 을 구간 앞뒤로 읽어 `rx:` 증분을 구간 길이로 나눈다.
  `fe:`·`oe:` 증가 여부도 같이 본다.
- 앱: [박자] 로그의 타임스탬프 차로 창 길이를 구한다. `uart stats` 로 오류 계수를 확인한다.
- 둘이 같으면 앱은 결백하고, 부족분은 MCU 또는 버스 쪽이다.

## 9. 남은 일

- 0x220(ESP12)을 쓰려면 앱 기본 필터에 추가해야 한다. 실차에서 휠펄스 수신율이 유지되는지 보고 넣는다.
- 기동 시 필터 재등록이 MCU 전송 기억을 비우는지는 펌웨어 쪽 확인으로 확정한다(현재는 관측만).
